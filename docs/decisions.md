### ADR-02 Prisma 7 with the better-sqlite3 driver adapter
- **Decision:** Prisma 7.10.0 with `prisma.config.ts`, generator `provider = "prisma-client"` and explicit `output = "../src/generated/prisma"`, `PrismaBetterSqlite3` adapter, `dotenv` loaded explicitly. All raw SQL lives in `src/server/db/raw/`.
- **Why:** Prisma 7 is the current stable line and moves the engine to JS driver adapters, which keeps the worker light. The single-statement job claim needs `$queryRaw` with `RETURNING`, which SQLite supports.
- **Risk:** PRAGMA scope per connection, DateTime storage format seen by raw SQL, and Windows prebuilds were UNVERIFIED (critic 12.3) until the M1 spike (T02); now verified, see ADR-02a.
- **ADR-02a (T02 spike result, 2026-10-15): PASSED, no fallback.** Pinned stack works unchanged on Windows 11 / Node 22.23.2 / npm 10.9.8 with no C++ compiler. Prebuilt binaries: better-sqlite3 12.11.1 via prebuild-install (SQLite 3.53.2, ABI 127); @node-rs/argon2 2.2.2 via @node-rs/argon2-win32-x64-msvc; sharp 0.35.5 via @img/sharp-win32-x64 (libvips 8.18.7). PRAGMAs confirmed on every adapter connection, including inside `$transaction`: journal_mode=wal (persisted in file), busy_timeout=5000, foreign_keys=1 (enforced). DateTime is stored as ISO-8601 text with a `+00:00` suffix (e.g. `2026-10-15T10:00:00.000+00:00`); bound Dates in raw SQL match it, so raw SQL always binds Dates and never relies on CURRENT_TIMESTAMP. Raw INTEGER columns come back as number, BIGINT/SUM/COUNT as bigint. One connection per PrismaClient; interactive transactions are serialized in-process. Two-process claim race: 200 jobs, each claimed exactly once, 0 SQLITE_BUSY. Paths with spaces work unencoded in `file:` URLs. Tests: `tests/integration/spike/*.test.ts` (15/15, 6 consecutive green runs).
- **Alternatives:** Prisma 8.0 rc (rejected: pre-release); Drizzle or Kysely (rejected: PRD default is Prisma; raw-SQL isolation already gives portability).
- **Reversibility:** 2.

### ADR-04 One process, one APP_MODE, one DB file per mode (C20, A4)
- **Decision:** `APP_MODE=demo|live` read once at boot. Each mode has its own DB at `<DATA_DIR>/<mode>/app.db`. `Workspace.mode` stays as defense in depth, checked by simulators and the adapter registry. LIVE excludes the role switcher from the bundle and 404s demo and test routes.
- **Why:** Makes "simulations cannot touch live data" structural rather than a query filter that one bug can bypass.
- **Alternatives:** shared DB with `Workspace.mode` (A5 in 01-arch; rejected by C20).
- **Reversibility:** 3.

### ADR-05 DispatchAttempt outbox; the reaper decides ambiguity (C7, C8, A9)
- **Decision:** One `DispatchAttempt` table with states QUEUED, SENDING, SENT, FAILED, SKIPPED, AMBIGUOUS, CANCELLED; `idempotencyKey` UNIQUE. SENDING is committed before any provider call. A lease-expired job holding a SENDING attempt becomes AMBIGUOUS + job DEAD in one transaction; otherwise the job is requeued. AMBIGUOUS resolves only on positive provider evidence or an audited operator action. Job states: QUEUED, RUNNING, SUCCEEDED, DEAD, CANCELLED. Claiming is a single `UPDATE ... RETURNING` statement.
- **Why:** Four reviewers designed this four ways (SendIntent, MessageDispatch, dispatchAttemptedAt). One mechanism is the only way to guarantee "no blind resend after ambiguous timeouts" and is the top implementation risk.
- **Amended by:** ADR-39 (claimToken fencing of every job-driven tx), ADR-40 (superseded-version settle), ADR-41 (failure classes), ADR-45 (persisted send intent).
- **Alternatives:** handler-side SENDING to UNKNOWN conversion (rejected by C8: a requeued unsafe job looks like "retrying"); pg-boss style queue (rejected: SQLite).
- **Reversibility:** 1 for the semantics, 4 for the queue implementation (behind `jobs/queue.ts`).

### ADR-06 Stop and unsubscribe are processed synchronously in the verified route (C9, A11)
- **Decision:** After signature verification, the WhatsApp webhook route detects `AL_QR_STOP_V1` or a STOP keyword (fixed list incl. `बंद`, `रोकें`, `stop`, `unsubscribe`) and, in the same transaction, inserts the WebhookEvent and Suppression, cancels QUEUED attempts and jobs for that contact and channel, and writes the audit row. The email unsubscribe route does the same. This is the single exception to "webhook routes only verify, persist, enqueue".
- **Why:** PRD says "immediate suppression". With the worker down (the 2am case), a job-based Stop would let queued outreach run on restart.
- **Alternatives:** Stop via a job (rejected). Do not "fix" this exception in later reviews.
- **Reversibility:** 4.

### ADR-07 Money is BigInt paise (C11, A1)
- **Decision:** Every `*Paise` column is Prisma `BigInt`; the domain uses `bigint`; DTOs serialize decimal strings. Sanity cap ₹100 crore per quote, configurable, over cap routes to review.
- **Why:** PostgreSQL `Int` caps near ₹2.14 crore in paise, and seeded property agencies can exceed it. Issued quotes freeze the representation, so it must be right before M2.
- **Alternatives:** Prisma `Int` with a ₹1 crore cap (05-ops 9.7; rejected by C11); Decimal (rejected: float-adjacent APIs, no need for fractional paise).
- **Reversibility:** 1.

### ADR-08 Quote PDFs via @react-pdf/renderer in a worker job (C1, A27)
- **Decision:** `quote.renderPdf` runs when a QuoteVersion is created, from one `buildQuoteRenderModel(snapshot)` that also feeds the HTML presenter. Output stored as `QuoteArtifact(quoteVersionId, sha256, path)`; footer prints version and short hash; Inter TTF with U+20B9 embedded. The share PDF route serves the stored file or returns 503 + Retry-After and enqueues a render.
- **Why:** No Chromium binary on Windows or a future host, no HTML engine (removes the file:// / SSRF / XSS class), worker stays about 150 MB, durable artifact supports restart consistency and hash parity tests.
- **Alternatives:** Playwright Chromium `setContent` (01-arch A8) or an internal print route with `render_token` (02-errors G-Q-2), both rejected; render at request time (05-ops 7.8, rejected: no durable artifact).
- **Reversibility:** 4 (behind the PDF port).

### ADR-09 Share credential is the path segment; state-specific responses (C2, C3, A28)
- **Decision:** `/quote/[token]`, token = 32 random bytes base64url, only `sha256(token)` stored in `QuoteShare(tokenHash UNIQUE)`. Invalid, revoked and cancelled render the identical 404. Expired and superseded render 410 naming the sender. `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store`, `X-Robots-Tag: noindex`.
- **Why:** Matches the PRD route shape without leaking a DB id; query strings land in more logs; hash lookup of a 256-bit token needs no constant-time compare; revocation must not confirm a link existed.
- **Alternatives:** `/quote/[id]?k=` (03-security T12, rejected).
- **Reversibility:** 3 (links already sent would break).

### ADR-10 VIEWED via beacon; accept via token + nonce + Origin (C4, C5, A29, A30)
- **Decision:** GET only appends `QuoteViewEvent(kind=FETCH)`. VIEWED transitions on a beacon POST from the rendered page after 2 s of visibility, with UA-class exclusion as a second filter, labelled "Opened (may be automated)". Accept is a POST with the token in the body, `formNonce = HMAC(SHARE_NONCE_KEY, tokenHash || versionId)`, Origin equal to APP_ORIGIN and `expectedVersionId`; idempotent per version. Manual "Copy link" / "Mark as sent" moves APPROVED to SENT (P15).
- **Why:** Link previewers and mail scanners fetch URLs and spoof browser UAs; the PRD forbids claiming human engagement.
- **Alternatives:** first browser-UA GET (rejected); cookie CSRF on a public route (not applicable).
- **Reversibility:** 4.

### ADR-11 Own email+password auth with DB sessions, not Auth.js (A31)
- **Decision:** argon2id via `@node-rs/argon2`, DB sessions (token hash stored), `__Host-` cookie, invite onboarding, super-admin issued resets when no email provider, login lockout persisted on `User`. MFA is a stated limitation.
- **Why:** Auth.js Credentials forces JWT sessions, which makes server-side revocation on role change awkward; membership and role are resolved from the DB per request anyway; no OAuth in scope; about 300 owned lines are easier to audit. `@node-rs/argon2` has Windows prebuilds (no node-gyp).
- **Alternatives:** Auth.js (rejected), Lucia-style library (rejected: maintenance status, small gain).
- **Reversibility:** 3 (behind `server/auth`).

### ADR-12 In-process rate limiting; only login lockout persisted (C6, A35)
- **Decision:** `withRateLimit()` token bucket in node-runtime handlers, documented as single-instance. `User.failedLoginCount` and `lockedUntil` are the only persisted counters, written on failure only.
- **Why:** A DB write per public request competes for the single SQLite writer with webhooks and the worker, the top contention risk. Login lockout must survive restarts.
- **Alternatives:** SQLite `RateLimitBucket` table (02-errors G-SEC-2, 03-security T13; rejected by C6); Redis (out of scope locally; documented PG/multi-instance path).
- **Reversibility:** 4.

### ADR-14 Email for Maps leads: opt-in, or attested B2B manual-only (user decision D4 / M2, 2026-10-15)

### ADR-15 Consent captured at ingestion; re-opt-in ordering (P1, P13, O2, A16, A19)
- **Decision:** Sheets and Meta form mappings may define a consent field (column or question key, truthy values, verbatim notice text hashed). A truthy value creates `ConsentRecord(basis=OPT_IN, source=SHEETS_FORM|META_FORM, evidence, noticeTextHash, collectedAt=submission time)`. No mapping or falsy value means no consent. Maps leads get no WhatsApp consent. Inbound WhatsApp creates service-window consent only. A suppression is cleared only by a new OPT_IN record with `collectedAt > suppression.createdAt` strictly; backfilled or undated evidence never clears it.
- **Why:** Without capture, no Sheets or Meta lead could ever become WhatsApp-eligible; without strict ordering, a delayed form row could silently undo a Stop. ConsentRecord carries `noticeVersion`, `noticeTextHash`, `withdrawnAt`, `withdrawalMethod` now so DPDP notice duties do not need a migration later.
- **Amended by:** ADR-37: "newer than the suppression" means newer than the latest Stop for that contact and channel, and suppression rows are append-only history.
- **Alternatives:** manual employee grant only (rejected: dead messaging path).
- **Reversibility:** 2.

Authoring and submission happen in WhatsApp Manager, linked from docs. DEMO seeds approved and rejected templates.

### ADR-18 AI: no silent fallback in LIVE; strip-and-flag proposals (C12, C13, A24-A26)
- **Decision:** In LIVE, an AI provider failure gets one repair retry, then NEEDS_REVIEW plus an explicit "Generate with local template" action labelled `local-deterministic`. DEMO uses the local generator by default. The proposal schema holds service IDs, quantities, scope and timeline only; any price, discount or tax key is stripped, flagged (`ai_price_ignored` etc.), audited, and the draft is forced to review. An output policy runs on every generated string; the auto-reply guard deflects out-of-scope intents.
- **Why:** PRD "never silently fall back"; AT5 "ignored and server price used"; treating the attempt as an injection signal without losing a usable proposal.
- **Alternatives:** auto fallback to the deterministic generator (03-security T10, rejected); reject the whole proposal (loses work); clamp AI discounts (moot: no discount field).
- **Reversibility:** 4.

### ADR-19 Suppression key is an HMAC with a server pepper (C17, A7)
- **Decision:** `Suppression(workspaceId, channel, contactKey)` with `contactKey = HMAC-SHA256(SUPPRESSION_PEPPER, normalized contact)` (uniqueness applies to active rows only, see ADR-37), plus an optional plaintext column nulled on lead erasure. Keyed on contact, not lead, so merges, re-imports and erasure cannot drop it. LIVE refuses to boot without the pepper; it is backed up with the key ring.
- **Why:** A plain sha256 of an Indian mobile number is reversible by enumeration in minutes. With a pepper the key is pseudonymous (stated as such in `/docs/data-retention`).
- **Alternatives:** plaintext normalized contact (rejected), plain sha256 (rejected).
- **Reversibility:** 2 (re-keying needs the old pepper).

### ADR-20 DB, storage and backups outside OneDrive (A5)
- **Decision:** Default data dir `%LOCALAPPDATA%\auralead\<mode>\` (`app.db`, `storage\`, `backups\`, `outbound.lock`), overridable by env. Boot warns if a resolved path contains `OneDrive`. Test DBs in `os.tmpdir()`. Backups via `VACUUM INTO`, never a file copy.
- **Why:** The repo is in a OneDrive-synced folder with a space in its path; OneDrive sync corrupts WAL databases, locks `-wal`/`-shm` files and uploads PII to the cloud.
- **Alternatives:** DB in repo `prisma/` (rejected).
- **Reversibility:** 5.

### ADR-22 Restore procedure pauses outbound and reconciles (O1)
- **Decision:** `npm run db:restore` writes `STORAGE_DIR/outbound.lock` first (worker honors it alongside the DB flag and env), restores the `VACUUM INTO` snapshot, marks every non-terminal DispatchAttempt created before the backup time as AMBIGUOUS, replays SuppressionJournal entries newer than the backup timestamp (ADR-38; this replaces the earlier "append-only audit export", which did not exist), and leaves outbound paused until an operator unpauses.
- **Why:** A restored backup can re-queue completed sends and erase later suppressions.
- **Reversibility:** 4.

### ADR-23 Approval binds to the exact outbound payload (O3)
- **Decision:** `Approval.payloadHash = sha256(canonical JSON of channel, destination key, template name + language, variables, body, subject, attachment {quoteVersionId, artifact sha256})`. Dispatch preflight recomputes it and refuses on mismatch with `APPROVAL_STALE`. Applies with or without a quote.
- **Why:** Binding only to the quote version lets the message text or recipient change after approval.
- **Reversibility:** 3.

### ADR-24 GatedAction gates only on configuration, permission, mode or eligibility (O4)
- **Decision:** The `reason` prop is a typed union of those four categories. Missing implementation fails milestone acceptance and may not be presented as a restriction. Lint bans `TODO`, "coming soon" and empty handlers in UI code; navigation omits unbuilt sections until their task lands.
- **Why:** Otherwise the truthfulness rule can be met on paper while features are missing.

### ADR-25 Credential encryption with a key ring (A33)
- **Decision:** AES-256-GCM, 12-byte nonce, envelope `v1.<kid>.<nonce>.<ct>.<tag>`, AAD `workspaceId|integrationId|field`, `CREDENTIALS_KEYRING` + `CREDENTIALS_ACTIVE_KID`, `npm run creds:rotate`. Masked reads only, no reveal endpoint. LIVE refuses boot without keys; `npm run setup` generates demo keys into `.env` (ADR-44). The same ring encrypts webhook processing payloads (ADR-35).
- **Why:** PRD requires encryption with a deployment secret plus rotation and revocation; AAD stops ciphertext swaps across tenants.
- **Reversibility:** 3.

### ADR-26 Mutations through route handlers, not Server Actions
- **Decision:** All cookie-authenticated mutations go through `/api/app/*` and `/api/admin/*` route handlers wrapped by `withRoute()` (size cap, auth, rate limit, Origin + signed double-submit CSRF, Zod, ctx). RSC pages read through services. No Server Actions for mutations.
- **Why:** One CSRF model, one error mapping, and every mutation is reachable by the generated HTTP tenant matrix.
- **Alternatives:** Server Actions with Next's Origin check (rejected: second auth path to test).
- **Reversibility:** 4.

The approval node is mandatory; POLICY_AUTO is selectable only when workspace auto-send is on, and dispatch checks still run. The graph is a validated list over five fixed stage kinds; no general workflow language.

### ADR-29 Window and delivery-status rules (C19, C10, A12, A13)
- **Decision:** Store `Conversation.lastInboundProviderAt` updated only by `max()`; `windowOpen(now) = now < lastInboundProviderAt + 24h`, exclusive, safety margin 0. Delivery status is rank-monotonic (pending < sent < delivered < read); `failed` changes state only at rank <= sent; later failures are stored as events with an anomaly flag.
- **Why:** A late older inbound can never shrink the window; deterministic merge is property-testable.
- **Reversibility:** 3.

### ADR-30 Provider error handling is table-driven and dated (C16, 12.3, A14)
- **Decision:** `adapters/whatsapp/error-map.ts` holds every provider code with a check date. 131049 maps to FAILED(`RECIPIENT_FREQUENCY_CAP`), back to review, manual retry only after 24 h, no automatic retry. 131026 maps to FAILED(`UNDELIVERABLE`), no retry, no suppression. No tier enums anywhere; quality and limits are stored as raw provider values. All codes are UNVERIFIED until checked and recorded in `docs/integrations.md`.
- **Why:** Auto-retrying a frequency-capped user degrades number quality; vendors disagree on code semantics.
- **Alternatives:** defer 24 h with one auto retry (02-errors, rejected by C16).
- **Reversibility:** 5.

### ADR-31 Quote math: half-up, document-level discount, one tax line (A1, A2, P8)
- **Decision:** Integer paise, rates in basis points, `mulDivHalfUp(a, bps) = (a*bps + 5000) / 10000`. Discount on the subtotal, tax on the discounted subtotal, each derived amount rounded once. One configured tax line; quotes say "Quotation, not a tax invoice"; explicit "no tax" setting required. Human over-limit discount 422 at the workspace limit, 403 beyond the actor's capability.
- **Why:** Reproducible by hand, matches AT5 (2,124,000 paise), avoids implying a GST invoice.
- **Alternatives:** banker's rounding (rejected), per-line tax (rejected), CGST/SGST/IGST split (out of scope).
- **Reversibility:** 1 (issued quotes freeze it).

### ADR-35 Webhook events keep an encrypted processing payload (E1)
- **Decision:** `WebhookEvent` stores `payloadRedacted` (inspector view) and `processingPayload`: the full parsed body encrypted with AES-256-GCM under the credentials key ring, AAD = `webhookEventId`. Workers decrypt only the processing payload. `webhook.purge` nulls it (`processingPurgedAt`) after successful processing plus a retention window (default 7 days; failed or unrouted events keep it until resolved or 30 days).
- **Why:** With only a redacted copy, a worker restart between persist and process loses the contact data needed to create the lead.
- **Alternatives:** store the raw body in plaintext (rejected: PII at rest in the inspector table); process inline in the route (rejected: violates verify, persist, 200).
- **Reversibility:** 4.

### ADR-36 Webhook idempotency is scoped by the authenticated source (E2)
- **Decision:** UNIQUE `(provider, scopeKey, externalKey)` where `scopeKey` is the routed `integrationId`, else the workspace of the authenticated token, else `unrouted`. A non-null scope column avoids SQLite's NULL-distinct uniqueness.
- **Why:** Sheets event ids and extension batch ids are client-generated; a global key lets one tenant's id block another's ingestion.
- **Reversibility:** 3.

### ADR-37 Suppression is append-only history (E3)
- **Decision:** Suppression rows carry `createdAt`, `clearedAt`, `clearedByConsentId`. PARTIAL UNIQUE on `(workspaceId, channel, contactKey) WHERE clearedAt IS NULL`. A re-opt-in clears the active row; a later Stop inserts a new active row. Re-opt-in evidence must be strictly newer than the latest Stop (active or cleared). Rows are never deleted.
- **Why:** With one unique row per contact, a second Stop after re-opt-in was undefined and old consent could be replayed against it.
- **Reversibility:** 2.

### ADR-38 SuppressionJournal outside the database (E8)
- **Decision:** `messaging/suppression.ts` is the only writer of Suppression rows. After commit it appends an fsynced JSONL line to `<DATA_DIR>/<mode>/journal/suppressions-YYYYMMDD.jsonl` with `journalId, workspaceId, contactKey, channel, action STOP|CLEAR, reason, createdAt, sourceEventId, suppressionId, consentId?`. If the append fails, the row's `journaledAt` stays null and `suppression.journalReconcile` re-exports it (idempotent by journalId). `db:restore` replays entries newer than the backup timestamp. Producer: T18, T20. Consumer: T24, tested against the real producer.
- **Why:** The restore procedure (ADR-22) depended on an "audit export" that nothing produced. A file outside the DB survives a DB restore.
- **Alternatives:** replay from AuditEvent (rejected: restored together with the DB, so later entries are lost).
- **Reversibility:** 4.

### ADR-39 Lease fencing inside every job-driven transaction (E5)
- **Decision:** Every transaction a job handler opens (preflight, settle, fail, domain writes) begins with a write-first fence `UPDATE "Job" ... WHERE id=? AND claimToken=? AND status='RUNNING'`. Zero rows throws `LeaseLostError` and rolls back before any domain write or provider call.
- **Why:** Checking the token only at final settle lets a worker that lost its lease run preflight and call the provider after another worker reclaimed the job.
- **Reversibility:** 4.

### ADR-40 Dispatch settle does not move a superseded quote (E6)
- **Decision:** Settle runs `UPDATE Quote SET status='SENT' WHERE id=? AND currentVersionId = attempt.quoteVersionId AND status='APPROVED'`. If no row changes, it sets only `QuoteVersion.sentAt` on the attempt's version and audits `quote.sent_superseded_version`.
- **Why:** A v1 send settling after v2 was revised and approved would otherwise mark v2 SENT without it being sent.
- **Reversibility:** 4.

### ADR-41 Dispatch failure classes (E7)
- **Decision:** `DispatchAttempt.failureClass` is PRE_SEND (definite pre-write failure), RETRYABLE (definite safe-to-repeat rejection: HTTP 429, 5xx with no-write evidence per the error map, SMTP 4xx) or PERMANENT (non-retryable 4xx). PRE_SEND and RETRYABLE requeue the job with backoff (honoring Retry-After; 429 also sets a throttle window); the retry is a new attempt N+1 that re-runs preflight. PERMANENT is never retried. Every error-map entry declares its class. Timeouts after write remain AMBIGUOUS.
- **Why:** Definite retryable rejections had no transition between "permanent failure" and "ambiguous".
- **Reversibility:** 4.

### ADR-42 workspaceId on every tenant table and same-workspace reference checks (E10)
- **Decision:** All tenant-owned tables, including children (PriceEntry, QuoteItem, JobAttempt, PipelineStageRun), carry `workspaceId`. Services call `assertSameWorkspace(tx, ctx, refs)` on every referenced id inside the transaction (404 on mismatch). Composite FKs `(workspaceId, parentId)` are used where Prisma 7 and SQLite accept them; T03 records which. The tenant matrix injects workspace B ids into mutation bodies.
- **Why:** Child rows without workspaceId allowed cross-tenant references that the scoped client could not catch.
- **Reversibility:** 1.

### ADR-43 Single pipeline orchestrator from M2 (E9)
- **Decision:** Ingestion enqueues only `pipeline.advance`. The executor (shipped in T10) reads the pinned PipelineConfigVersion, runs one stage at a time, and records `PipelineStageRun` with UNIQUE (executionId, stage). T12 and T14 register the SCORE and DRAFT stage handlers; T23 adds APPROVAL and DELIVERY and graph validation.
- **Why:** If ingestion enqueued score and draft jobs directly, the React Flow pipeline would be decorative and replays could run stages twice.
- **Reversibility:** 3.

### ADR-44 One env file and one loader (E12)
- **Decision:** `npm run setup` writes `.env` (gitignored) from `.env.example` with generated demo secrets and never overwrites existing keys. `src/lib/env-load.ts` loads `.env` without overriding real environment variables and is called first by `next.config.ts`, `prisma.config.ts`, the worker, the seed and every script. No `.env.local`.
- **Why:** The plan had setup writing `.env.local` while the worker loaded `.env`, so app and worker could disagree on secrets and DB path.
- **Reversibility:** 5.

### ADR-45 Send intent is persisted and checked at dispatch (E4)
- **Decision:** Message and DispatchAttempt carry `sendIntent` (MANUAL_SINGLE, BULK, AUTOMATED, CUSTOMER_REQUESTED_REPLY) and `initiatedBy`, set at creation and immutable. Eligibility reads the persisted intent. A new ordered check `AUTO_SEND_DISABLED` skips automated attempts when workspace auto-send is now off or the pinned pipeline is no longer POLICY_AUTO for attempts created by a POLICY_AUTO approval. An unapproved CUSTOMER_REQUESTED_REPLY counts as automated. Attested-B2B email requires MANUAL_SINGLE.
- **Why:** Without persisted provenance, dispatch could not tell automated work from manual sends, so disabling auto-send would not stop work already queued.
- **Reversibility:** 3.

### ADR-46 Test teardown kills the process tree first on Windows (T02)
- **Decision:** `tests/support/spawn.ts` `terminate()` runs `taskkill /T /F /PID <pid>` first on Windows and uses `child.kill('SIGKILL')` as the fallback (POSIX: SIGKILL). The plan text listed SIGKILL first with taskkill as the fallback.
- **Why:** On Windows `child.kill('SIGKILL')` terminates only the direct child; once the parent is gone, `taskkill /T` can no longer find the tree, so grandchildren would be orphaned. `tests/integration/spike/teardown.test.ts` asserts that both the child and its grandchild are gone.
- **Alternatives:** SIGKILL first plus per-test tracking of descendant pids (rejected: fragile).
- **Reversibility:** 5.

### ADR-47 Full schema: partial indexes via the Prisma preview feature, composite tenant FKs, small schema additions (T03)
- **Decision:**
  - **Partial unique indexes** are declared in `schema.prisma` with the `partialIndexes` preview feature (`@@unique([...], map: ..., where: raw("..."))`, Prisma 7.10.0) instead of SQL hand-written only in the migration. Prisma generates them into the migration SQL, where each one is still marked `-- PARTIAL UNIQUE`. There are eight: Suppression active row, one active PricingVersion, ScoringConfigVersion and PipelineConfigVersion per workspace, one APPROVED quote-version Approval per version, one PENDING or APPROVED Approval per message, one open Conversation per (workspace, lead, channel), and one unrouted WebhookRejection counter per (provider, reason, day).
  - **Composite foreign keys** `(workspaceId, parentId) -> parent(workspaceId, id)` are accepted by Prisma 7.10 and SQLite for every tenant child-to-parent reference, including optional ones. The parent carries `@@unique([workspaceId, id])`. `tests/unit/arch/tenant-columns.test.ts` enforces this for every reference between tenant models.
  - **Service-enforced, not foreign keys:**
    - `Suppression.clearedByConsentId`, because a suppression must survive lead erasure.
    - Every `Job.workspaceId`, `JobAttempt.workspaceId`, `AuditEvent.workspaceId`, `WebhookEvent.workspaceId` and `WebhookRejection.workspaceId`, because these are nullable system rows.
    - `WebhookEvent.integrationId`, `PipelineStageRun.jobId`, `Session.activeWorkspaceId`, and the `createdBy`, `decidedBy` and `requestedBy` user-id columns.
  - **Additions the §5 tables did not spell out:**
    - `Conversation.closedAt` defines "open" for the open-conversation partial unique.
    - `Message.channel` is the provider namespace for `(channel, providerMessageId)` UNIQUE. `DispatchAttempt` uses the same `(channel, providerMessageId)` UNIQUE.
    - `WebhookRejection` gets an extra partial unique for null-workspace rows, because NULLs are distinct inside the plain unique.
    - `Quote.currentVersionId` is nullable, but only inside the creating transaction: Quote and QuoteVersion reference each other, and SQLite FKs are not deferrable.
    - `Quote.validUntil` is nullable until version 1 exists.
    - Inline value sets became enums: TaxMode, QuoteSentVia, UaClass (BROWSER, LINK_PREVIEW, BOT, UNKNOWN), MessageKind, TemplateIntent and ActorKind.
    - `Lead.pipelineConfigVersionId` is nullable for leads created before a pipeline exists.
  - **One-to-one uniques stay single-column:** `QuoteAcceptance.quoteVersionId`, `QuoteArtifact.quoteVersionId` and `PipelineExecution.leadId`. Their back-relations are lists, because Prisma requires a composite unique for a 1:1 over a composite FK.
- **Why:** If the indexes lived only in hand-written migration SQL, they would be invisible to Prisma's diff, and the next `prisma migrate dev` would emit `DROP INDEX` for them as drift. With the preview feature, `prisma migrate diff` from the migrated DB to the schema is empty (verified). The DB-level composite FKs back up `assertSameWorkspace` (E10).
- **Caveat:** The preview feature also exposes the partial-unique fields in the generated `WhereUniqueInput`; for example, `PricingVersion` accepts `where: { workspaceId }` and `Suppression` accepts `workspaceId_channel_contactKey`. Do not use them for `findUnique` or `upsert`, because they are unique only among the rows that match the predicate. Look up active rows with `findFirst` plus the predicate, such as `active: true` or `clearedAt: null`.
- **Alternatives:** Hand-written SQL only, as the plan text says. It was rejected because of the drift problem above. If the preview feature regresses, fall back to hand-written SQL and pass `--create-only` on every later migration so the DROP INDEX lines can be removed by hand.
- **Reversibility:** 3.

### ADR-48 Job runtime details the plan left open (T07)
- **Decision:**
  - **Worker bundle name.** The `build` script now runs `tsup --entry.worker worker/index.ts ...`. Before, it ran `tsup worker/index.ts`, which writes `dist/index.js`, while `start:worker` and the E2E harness run `dist/worker.js`. This is the only non-append edit to `package.json`. Verified: the bundle refuses to start on an unmigrated DB (exit 1) and starts on a migrated one.
  - **Handler contract.** A handler returns `succeeded | deferred | retry | dead | cancelled`, and any of these may carry a `finalTx`. The runner runs `finalTx` inside the fenced settle transaction, so a domain write and the job's final state commit together. Writes made earlier in a handler go through `ctx.fencedTx`. A thrown `AppError` with `retryable` (or `DB_BUSY`) is retried; `LEASE_LOST` is a lost lease; any other thrown error is fatal (`DEAD`, `deadReason = FATAL`).
  - **Max attempts per kind.** A job's limit is stored in `Job.maxAttempts` at enqueue time, taken from `kind` (send 5, ai 3, fetch 8, pdf 3, default 5) or set explicitly.
  - **Attempt numbers.** `JobAttempt.attemptNo` is sequential per job and does not follow `Job.attempts`. Deferrals refund `Job.attempts` (plan §4.3), so reusing it would collide on `(jobId, attemptNo)`. A deferral is logged as `DEFERRED`, a cancel as `FATAL` with `errorCode = JOB_CANCELLED` (the enum has no CANCELLED outcome), and a reaped lease as `LEASE_LOST` (or `AMBIGUOUS` when a SENDING DispatchAttempt existed).
  - **Reaper at max attempts.** An expired lease on the last allowed attempt goes `DEAD(MAX_ATTEMPTS)` instead of being requeued.
  - **Background writes are transactions.** Heartbeat, lease extension, claim and reaper writes all run through `withTx`. The adapter keeps one connection per client and serializes interactive transactions, so a background write can never land inside a handler's open transaction.
  - **Pause points.** They are file-based across processes: `AURALEAD_PAUSE_DIR` plus `AURALEAD_PAUSE_AT`, `<name>.reached.json` and `<name>.release`. In-process tests use `setPauseHandler`. All of this is a no-op unless `NODE_ENV=test`. These test-only variables are not added to `.env.example`.
  - **Concurrency is 1.** The configurable concurrency of up to 4 for provider-bound types is not built yet. The task that first needs it (T19 or later) adds it behind `createWorker`.
- **Why:** The plan fixes the behavior (claim, fence, reaper, backoff, heartbeat, shutdown) but not these mechanics. Each choice is covered by `tests/integration/jobs/*.test.ts`.
- **Reversibility:** 4.

### ADR-51 Ingestion and pipeline executor details (T10)
- **Decision:**
  - **Service signature.** The service is `ingestBatch(ctx, input, deps)`, not the plan's `ingestBatch(ctx, source, records[])`.
    - `input` is `IngestBatchInput` from `src/lib/schemas/ingest`: `{source, externalBatchId, simulated?, extensionTokenId?, mapping?: {version?, formId?, consent?}, records[]}`.
    - `deps` is `{contactKeyPepper}`, which is SUPPRESSION_PEPPER. Consent records need the suppression contact key, and services do not read env.
    - The batch content hash is a sha256 over the canonical JSON of the parsed input.
  - **Stage-handler registry.** The registry lives in `src/server/services/pipeline/stages/` (`index.ts` holds the registry and `STAGE_HANDLERS`, plus `types.ts` and `ingestion.ts`). This directory is outside T10's listed Owns paths.
    - `index.ts` is append-only: T12 and T14 each add one import and one array entry.
    - A handler returns DONE, SKIPPED or FAILED. Its writes go in a `finalTx` that runs inside the job's fenced settle transaction, together with the StageRun update and the enqueue of the next stage.
  - **Job payload.** `pipeline.advance` has payload v1 `{executionId, stage}` and idempotency key `pipeline.advance:<executionId>:<stage>`, so there is exactly one job per stage.
    - A replay for a stage that is DONE, SKIPPED or FAILED runs nothing.
    - A stage FAILED by its handler stops the pipeline.
    - A retryable error is retried. Once retries are exhausted, or on any other thrown error, the stage is FAILED (`STAGE_RETRIES_EXHAUSTED` / `STAGE_ERROR`) and the job is DEAD.
  - **Missing stage handler.** A stage kind with no registered handler, such as APPROVAL and DELIVERY until T23, is recorded as PipelineStageRun PENDING with `STAGE_HANDLER_MISSING`, audited as `pipeline.stage.waiting`, and the execution waits there. It is never skipped, and the job is not DEAD.
  - **Website status.** A supplied, valid http(s) website gets PRESENT_UNVERIFIED. With no website the status is UNKNOWN. VERIFIED_ABSENT is never set at ingestion.
  - **Per-row rejection.** A record is rejected for `MISSING_NAME` or `NO_VALID_CONTACT` (no valid phone and no valid email).
    - Rejected records keep a REJECTED LeadSourceRecord.
    - Any later record with the same (source, externalId) reports DUPLICATE with `ALREADY_RECEIVED`.
    - A repeated externalId within one batch reports `DUPLICATE_IN_BATCH` and is not stored.
  - **Duplicate matches.** A record that matches exactly one lead is DUPLICATE (`CONTACT_MATCH`). The lead and its keys are not changed.
  - **Consent on duplicates and reviews.** Consent evidence from a duplicate row is recorded against the matched lead. A REVIEW record gets no consent, because there is no lead yet.
  - **Consent preconditions.** Consent capture needs a submission time; undated evidence is never recorded. Capture works only for GOOGLE_SHEETS (SHEETS_FORM) and META_ADS (META_FORM). Evidence is `{formId?, responseId, questionKey, mappingVersion?}`.
  - **Consent and suppression.** Capture does not clear suppressions. That ordering belongs to T18's suppression service.
  - **No active pipeline.** In a workspace without an active PipelineConfigVersion, the lead is still created. It gets no execution and no job, and its audit summary says `NO_ACTIVE_PIPELINE`.
- **Why:** The plan fixes the behavior (dedupe to review, per-record results, consent capture, the version pin, one orchestrator) but not these mechanics. Each item is covered by `tests/unit/leads/normalize.test.ts`, `tests/integration/ingest/*.test.ts`, `tests/integration/consent/consent-capture.test.ts` and `tests/integration/pipeline/executor-idempotency.test.ts`.
- **Reversibility:** 4.

### ADR-52 Pricing catalog, settings and server-side totals details (T13)
- **Decision:**
  - **Who may change pricing.** Catalog and settings mutations require the `pricing.override` capability, which among workspace members only the OWNER holds (MEMBER capabilities exclude it). The `/api/app/pricing/*` routes are USER-panel routes (`roles: ['USER']`); reads (`GET /api/app/pricing` and the page) are open to any member, who sees the data read-only with the controls gated by permission (plan §12). The plan names no dedicated "pricing.manage" capability.
  - **What publishes a version.** Every change to the price list (a service added, a price or min/max quantity changed, a service removed from the list) publishes PricingVersion N+1: the active version's entries are copied with the change applied, the old version is deactivated and never edited. Name, description, unit label, typical timeline and per-service discount limit are Service columns and are edited in place (audited, no new version); issued quotes keep their own snapshot (QuoteItem.serviceNameSnapshot, QuoteVersion.snapshot). Every mutation carries `expectedVersion` (the active version number the editor saw, 0 when none); a mismatch is 409 `PRICING_VERSION_CONFLICT`.
  - **Delete = archive if referenced.** A service is referenced when any QuoteItem or any PriceEntry (any version) points at it, so its history stays readable; it is archived (`archivedAt`) and dropped from version N+1. A service nothing references is deleted. A duplicate code (archived ones included) is 409 `SERVICE_CODE_TAKEN`; an archived service cannot be edited (422 `SERVICE_ARCHIVED`). Restoring an archived service is not built (not in the plan).
  - **Validation split.** Zod schemas (`src/lib/schemas/pricing.ts`, new, shared by the routes and the page forms) check shape only, so domain violations answer 422 with a code instead of a Zod 400: negative or above-₹100-crore unit price and quantity bounds (1 <= min <= max <= 10000) `AMOUNT_INVALID`; tax `TAX_NOT_CONFIGURED` / `TAX_RATE_INVALID` / `TAX_LABEL_INVALID`; `DISCOUNT_LIMIT_INVALID`; `VALIDITY_INVALID` (1..365 days); `GSTIN_INVALID` (format only, stored upper-case, P8).

### ADR-53 Scoring, website enrichment and safeFetch details (T12)
- **Decision:**

T14 (AiDraft) uses ADR-54.

There is no simulated website result, because that would fake a provider result. Enrichment also never re-checks a VERIFIED_ABSENT lead (a person's decision) and never sets that status. The host is pinned by an undici `Agent` whose connector swaps the hostname for the validated address (SNI and Host keep the hostname). It is not pinned with `connect.lookup` as plan §2 words it; the effect is the same and there is no second resolution. `lookup` and `connectTo` are test seams (stub DNS, land the pinned public address on a local server) that production never passes. A body over 1 MB is cut there and the head is kept (`truncated: true`); it is not an error.
  - **Score semantics (schemaVersion 1, `src/lib/schemas/scoring.ts`).** The schema is new and outside T12's Owns list, because it is shared with the T26 config form (plan §2: one schema set), like `pricing.ts`. These are unknown (weight 0, listed in `unknownInputs`): missing rating or reviews, a website that is not REACHABLE or VERIFIED_ABSENT, a missing category or no configured targets, and a MANUAL source. A missing phone or email is a known 0. `SCORE_CAPTION` = "Heuristic fit score. Not purchase intent or consent."

### ADR-54 Source simulators and webhook persistence details (T11)
- **Decision:**
  - **Simulators use the webhook path.** `POST /api/demo/simulate/[source]` (`sheets`, `meta`, `gmaps`) builds the provider's own payload with a DEMO adapter and calls `persistWebhookEvent`, the same service the live receivers (T34-T36) will call. The worker's `ingest.process` job decrypts the processing payload and calls `ingestBatch`, so simulated leads get the same source record, batch, pipeline job and audit trail as live ones. Simulated events use the real provider enum (GOOGLE_SHEETS, META_ADS, GMAPS_EXTENSION) with `simulated = true`, not `WebhookProvider.DEMO`.
  - **Simulated integrations.** On first use, a Sheets or Meta simulation creates the workspace's Integration with status SIMULATED and **no `routingKey`**, plus a demo SheetMapping v1 or MetaFormMapping, each with a consent mapping (P1) and audit rows. Every simulated workspace shares one fictitious Page and form id, so identical leadgen ids in two workspaces give identical `meta:{page}:{leadgen}` keys, and only the scope key keeps them apart (E2). Extension simulations are scoped by workspace, as a token is.
  - **Payload formats are defined here (`src/lib/schemas/webhooks/`, a new path outside T11's Owns, per the plan §2 one-schema-set rule).**
    - Sheets push v1: `{version, eventId, sheetId, mappingVersion, rows[{rowKey, submittedAt?, values}]}`, at most 50 rows.
    - Meta: `{change: <leadgen change value>, lead: <Graph lead with field_data>}`. The processing payload must contain the retrieved lead, because the webhook itself carries no contact data. T35's `meta.lead.fetch` either stores the fetched lead in this shape or calls `metaToIngest` directly.
    - Extension batch v1: `{version, batchId, keyword?, records[{recordId, placeId?, name, phone, email, website, address, city, category, rating, reviewCount, extractedAt?}]}`, at most 200 records.
    - T34-T36 may extend these formats but must keep `ingest.process` able to read events already stored.
  - **Body hash.** For live webhooks, `bodySha256` is the hash of the raw bytes. For simulations it is the hash of the canonical JSON (sorted keys). The same key with a different hash is 409 `BATCH_CONTENT_MISMATCH` for every provider, the code plan §9 names for the extension.
  - **Fencing.** `ingest.process` makes one fenced write (`WebhookEvent.attempts`) before calling `ingestBatch`. `ingestBatch` (T10) then writes in its own unfenced short transactions. This is a deviation from "every job-driven write is fenced" (ADR-39) and is accepted because ingestion is idempotent per batch and per record (UNIQUE ImportBatch and LeadSourceRecord): a worker that lost its lease can only replay stored results, never duplicate. The event's PROCESSED state, result, purge schedule and audit commit in the fenced settle.
  - **Failure handling.** An unreadable payload (decrypt or JSON), a payload that does not match its schema, a missing mapping, or a 4xx domain error from ingestion marks the event FAILED with a code. The job is SUCCEEDED (handled, not retried), and the purge is scheduled at receivedAt + 30 days. Retryable errors retry the job. Anything else is DEAD and the event stays RECEIVED for an operator.
  - **Purge.** The `webhook.purge` key is `webhook.purge:<eventId>`. The job runs at processedAt + 7 days, or receivedAt + 30 days for failed or unrouted events. A run before the due time defers to it. Purging keeps `payloadRedacted` and `result` (ids, statuses and codes only).
  - **Route access.** Roles are USER and EMPLOYEE with `leads.write`. The optional `workspaceSlug` body field is resolved through `buildUserContext` exactly like a `[ws]` segment (membership or active assignment), so a foreign slug is 404 and an in-tenant missing capability is 403.
  - **Lead console page (outside Owns).** The plan's T11 goal names "Employee lead console simulation buttons", but the console path `src/app/dashboard/employee/[ws]/leads/**` belongs to T17 (initial). T11 created the initial page with only the simulation panel, recent source events and the latest leads (read model `services/webhooks/console.ts`). T17 extends that page with detail, drafts, quotes and approval. The employee home cards (T09 file) gained an "Open lead console" link, because a `[ws]` page cannot be a static nav item.
  - **Other files outside Owns:** `src/lib/demo/contacts.ts` (deterministic fictitious people and businesses shared by the DEMO adapters and the extension simulator; no crypto, browser-safe).
- **Why:** The plan fixes the goals (simulators through the same services, scoped idempotency, encrypted processing payload, purge) but not these mechanics. Covered by `tests/integration/ingest/simulate-sources.test.ts`, `tests/integration/ingest/replay-idempotency.test.ts`, `tests/integration/webhooks/processing-payload-restart.test.ts`, `tests/components/leads/simulation-panel.test.tsx` and the tenant matrix.
- **Reversibility:** 4.

A workspace/process mode mismatch is refused. The plan's single `adapters/registry.ts` does not exist yet; this file is the AI part of it.

A refusal escalates to review (AiRefusalError); the Anthropic server-side refusal fallback (`fallbacks`) is deliberately not enabled, because the plan routes refusals to a person.
  - **Retry and review rules.** Retryable provider errors (429, 5xx/529, connection, timeout) are rethrown while job attempts remain and become NEEDS_REVIEW on the last attempt (`ai.draft` is kind `ai`, 3 attempts; the DRAFT stage runs inside `pipeline.advance`, kind `default`, 5 attempts). Auth, 404 model, other 4xx and refusals are NEEDS_REVIEW at once. Malformed, empty or truncated output gets exactly one repair call with the validation issues (max tokens x1.5 after truncation). A NEEDS_REVIEW draft still completes the DRAFT stage (DONE); review belongs to APPROVAL (T23).

Recipient-like keys (to, cc, bcc, recipients, phone, emailAddress, ...) are stripped too and flagged `ai_recipient_ignored`, so an injected send target never survives. Any other extra key is malformed output. One `ai.proposal.flagged` AuditEvent lists the flags and the stripped key paths; `ai.draft.generate` is written for every draft; `ai.draft.request` for the user action.
  - **Output policy rules.** CURRENCY_AMOUNT, PERCENTAGE, URL (server quote link allowlisted), PHONE and EMAIL (lead's own allowed), PAYMENT_PHRASING, DISCOUNT_OR_FREE_OFFER, CONTROL_CHARACTERS (incl. bidi), TEMPLATE_VARIABLE_FORMAT (WhatsApp variable rules, UNVERIFIED until T32). The plan's "off-catalog names" check is implemented as: proposal lines only by exact catalog id, plus the discount/free-offer phrasing rule; free-text mention of a service name is not matched. A violating field is not stored. `escalated` is set by any flag, violation, or proposal line outside the catalog.
  - **Untrusted inputs.** The context builder reads `Lead.websiteEnrichment.text` (T12) when `untrusted: true`, and takes inbound text from the caller (T21). Website text is capped at 4096 code points and messages at 2048, with control and bidi characters removed. Lead fact strings are capped at 200.

The routes and the "Generate with local template" button belong to T17/T22, which own `/api/app/leads/**` and the UI. The AI drafts rate limit (30/min/workspace, `RATE_LIMIT_POLICIES.aiDraft`) is applied by that route.
  - **`--ai` token lint rule.** In `eslint.config.mjs`, Literal and TemplateElement strings using the Tailwind `ai` color utilities (`text-ai`, `bg-ai/20`, `border-ai`, ...) or `--ai` / `--color-ai` are errors in `src/app/**` and `src/components/**`, including visual, except `src/components/ai/**`. ### ADR-56 Quote lifecycle details (T15)
- **Decision:**
  - **One Approval row per quote version.** Creating a version (v1 or N+1) inserts a `QUOTE_VERSION` Approval with status PENDING (the item an approval queue lists). Approve is a CAS on `status = DRAFT AND currentVersionNo = expectedVersion` and turns that row APPROVED (`decidedBy`, `decidedAt`). A revision or cancel marks every PENDING or APPROVED approval of the quote or its versions INVALIDATED with `invalidationReason` `QUOTE_REVISED` or `QUOTE_CANCELLED`. `flags` carries the version's AI policy flags plus `needs_pricing_review`. There is no reject action here; that belongs to T22's approval queue.
  - **Every edit is a new version.** All editable fields (items, quantities, discount, scope, timeline, validity) are material, so DRAFT -> DRAFT also creates N+1 (plan §6.1). In the same transaction, QUEUED DispatchAttempts on any version of the quote are CANCELLED with reasonCode `SUPERSEDED`, or `QUOTE_CANCELLED` on cancel. Their QUEUED jobs are CANCELLED, RUNNING jobs get `cancelRequestedAt`, and their PENDING Messages become NOT_SENT. Attempts already SENDING are left for the settle CAS (E6).
  - **A revision keeps the pricing version it revises.** It is priced against the revised version's PricingVersion unless `repriceToActive` is set. This way a catalog change never silently changes an offer being edited. The editor offers re-pricing when a newer price list exists.
  - **Approval guards (422).** `PRICING_REVIEW_REQUIRED` applies while `needsPricingReview` is set (a line without a price, or a total above the sanity cap); a revision clears it. `QUOTE_VALIDITY_PASSED` applies when `now >= validUntil`. AI proposal reasons (UNKNOWN_SERVICE, QTY_OUT_OF_BOUNDS, DUPLICATE_SERVICE, NO_ITEMS) are copied into `QuoteVersion.reviewReasons` with `source: 'ai_proposal'`, but they do not set `needsPricingReview` (plan §8). The draft's `aiPolicyFlags` are copied to the version and carried into later versions.
  - **Expiry scheduling.** No periodic scheduler exists, so each version enqueues `quote.expireSweep` for its validUntil. The key is `quote-expiry:<workspaceId>:<UTC minute>` and the job runs at the end of that minute, so every quote due in the bucket has lapsed by then. The plan's example key was the hour bucket `quote-expiry:2026-10-15T10`; per-workspace minute buckets give expiry within 60 s, and duplicate schedulers still collapse on the key. Each sweep expires every due APPROVED, SENT or VIEWED quote of the workspace, one CAS and one `quote.expire` audit each. Reads (`effectiveQuoteStatus`) show EXPIRED before the sweep runs, without writing.
  - **Share links.** `createQuoteShare` / `revokeQuoteShare` and the routes `POST /api/app/quotes/[quoteId]/shares` and `.../shares/[shareId]/revoke` need `dispatch.send`. Links can be created for APPROVED, SENT or VIEWED quotes within validity; otherwise the answer is 422 `QUOTE_NOT_SHAREABLE`. The token is returned once, and `expiresAt = min(validUntil, now + expiresInDays)` (P16). Creating a link does not move the quote to SENT. The share UI (create, copy-marks-SENT, revoke) is T22's, so the detail page lists link states read-only.
  - **Routes are USER-panel only** (`roles: ['USER']`; capabilities `quotes.edit`, `approvals.decide`, `dispatch.send`). T17's employee console calls the same services from its own `[ws]` routes.
  - **Files outside the Owns list:**
    - `src/lib/schemas/quotes.ts`: the shared Zod schemas, per the one-schema-set rule.
    - `src/server/services/approvals/quote-approvals.ts`: the quote part of approvals/**.
    - `prisma/seed/fixtures/quotes.ts` and the `insertQuotes` step in `seed.ts`: one lead and a DRAFT quote v1 in workspace B, so the tenant matrix probes a real foreign quote. Lead, Quote, QuoteVersion and Approval times were added to `REBASE_COLUMNS`.
    - The "Quotations" nav item.
    - The quote status badge, which lives beside the pages and reuses the shared tone tokens.
- **Why:** The plan fixes the state table, invalidation, CAS and P16 rules, but not these mechanics. Covered by `tests/unit/quotes/state-machine.test.ts`, `tests/integration/quotes/{snapshot-and-approval,version-conflict,expiry,seed-quotes,pages}.test.ts`, `tests/components/quotes/quote-editor.test.tsx` and the tenant matrix.

### ADR-57 Quote PDF and public quote details (T16)
- **Decision:**
  - **`/quote/[token]` is a route handler, not a `page.tsx`.** The file is `src/app/(public)/quote/[token]/route.ts`. AT7 needs 410 for expired and superseded links and 429 over the public limit. App Router pages can only answer 200, 401, 403 or 404, and `proxy.ts` may not read the DB.
    - The handler renders `PublicQuotePage` (which wraps `QuoteDocument`) to a complete HTML document.
    - It uses `src/components/quote/static-markup.ts`, a small escaping serializer for presentational element trees. `react-dom/server` cannot be loaded in the React Server Components layer where route handlers run.
    - The serializer refuses event handlers, raw HTML, unsafe attribute names, and `<script>`/`<style>` text that is not a constant string or that contains a closing tag.
    - The page does not use Next's client runtime. Its one script is a constant that handles the 2 s visibility beacon, print, and a JSON submit of the acceptance form; it gets page data only from data attributes. With JavaScript off, the page says to download the PDF and reply to the sender.
    - The DEMO role switcher is not on this customer-facing page; P19 lists `/`, `/docs` and the panels.
    - The route manifest lists the file with kind `api`.
  - **Public-page headers.** The handler sets a CSP based on sha256 hashes instead of a nonce, so every 404 body is byte-identical (C3). It also sets `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store`, `X-Robots-Tag: noindex`, nosniff and `X-Frame-Options: DENY`.
    - `next.config.ts` (a T01 file) gained a `/quote/:path*` and `/api/quote-share/:path*` header rule. Without it the global `Referrer-Policy` overrode the handler's value in the built app; the E2E spec caught this.
  - **Share states (C3).** These all render the same 404:
    - a malformed or never-issued token;
    - a revoked link;
    - a cancelled quote;
    - an unissued (DRAFT) quote.

    These render 410 naming the sender (`ShareGoneError`, codes `SHARE_LINK_EXPIRED` or `SHARE_LINK_SUPERSEDED`):
    - a superseded link, or a link whose version is no longer current;
    - a link past `expiresAt`, or a quote past `validUntil`.

    An ACCEPTED quote stays viewable through links to the accepted version. The JSON routes under `/api/quote-share/[token]/{view,accept,pdf}` use the same resolution.
  - **One rate-limit bucket.** `publicQuote` (30/min/IP), keyed `quote:<ip>`, covers the page, beacon, accept and PDF routes together.
  - **View evidence (C4).** A page GET appends `QuoteViewEvent(FETCH)` only. The beacon appends `BEACON` events, and what else it does depends on the case:
    - User agents classed LINK_PREVIEW or BOT never move a quote.
    - A browser or unknown agent on a SENT quote moves it to VIEWED (CAS) and writes the audit `quote.view` (label "Opened (may be automated)").
    - On an APPROVED quote it returns the hint "Mark as sent?" and writes `quote.view.unsent` once per link.
  - **Acceptance (C5).**
    - The route checks Origin first (withRoute). The body token must equal the path token (404). The form nonce is verified before any DB read (403 `FORM_NONCE_INVALID`, also when the nonce is missing).
    - A stale expected version is 409. Accepting an APPROVED quote that was never sent is 409 `INVALID_TRANSITION`; the page shows no form in that state.
    - In one immediate transaction it writes QuoteAcceptance, then a CAS to ACCEPTED with `acceptedVersionId`, then moves the lead's sales stage forward to CONVERTED (only from NEW, CONTACTED, REPLIED or QUOTE_SENT), then writes one `quote.accept` audit row. The audit stores no name.
    - A repeat or a parallel accept returns the stored receipt.
  - **Hash in the footer.** It is the first 12 hex characters of `contentHash`, a sha256 over the canonical JSON of the render model (quote number, version, dates, sender, recipient, lines, totals, scope, timeline, terms, notice), excluding the watermark. A PDF cannot carry its own file hash. `QuoteArtifact.sha256` is the file hash and is checked on every read.
  - **Document snapshot.** `createQuote` and `reviseQuote` (T15's `versioning.ts`) now store `snapshot.document`: sender name, time zone, brand colour, terms, GSTIN and recipient name. Plan §5.4 says the snapshot carries "branding refs". With this, a later branding or lead edit cannot make the stored PDF and the HTML page disagree. Older versions, such as the T15 seed quote, fall back to the live rows.
  - **Render job enqueue.** The same two functions enqueue `quote.renderPdf`, keyed `quote.renderPdf:<versionId>` (kind pdf), in the version-creating transaction. These T15-file edits are the only changes to T15 code.
  - **Artifacts.**
    - Path: `STORAGE_DIR/quotes/<workspaceId>/<quoteVersionId>.pdf`, written to a temp file and renamed into place.
    - Rendering is deterministic: the creation date is the version time, and the pdfkit id and subset tags derive from the content. A re-render after a crash writes identical bytes.
    - A missing artifact row gives 503 + `Retry-After: 5` and enqueues the render. A row whose file is missing or altered gives 500 `ARTIFACT_INTEGRITY` and is never served.

### ADR-60 Dispatch outbox, approve-and-send and the transaction lint rule (T19)
- **Decision:**
  - **No route in T19.** T19's Owns list has no route path; `/api/app/{approvals,messages,conversations}/**` belong to T22. AT12's "10 concurrent approve-and-send from 2 clients" is tested at the service: ten calls on two separate Prisma clients (two connections contending on the SQLite write lock) return the same `{approvalId, messageId, attemptId, jobId}`, with `created: true` exactly once. T22's routes wrap `approveAndSendQuote` / `approveAndSendMessage` and answer 200 with those ids.
  - **Approve-and-send shape.**
    - `approveAndSendQuote(ctx, {quoteId, expectedVersion, channel, templateId?, variables?}, {contactKeyPepper})` needs `approvals.decide` and `dispatch.send`.
    - In one transaction it approves the current version when it is DRAFT (same CAS and guards as `approveQuote`, through `nextQuoteStatus`). An APPROVED quote is sent as is; any other status is 409 via `nextQuoteStatus(status, 'SEND')`.
    - It then creates the Message (PENDING, `sendIntent = MANUAL_SINGLE`, `initiatedBy = <userId>`) and binds the version's own QUOTE_VERSION approval to it (`messageId`, `payloadHash`). A second channel for the same version gets its own APPROVED OUTBOUND_MESSAGE approval. It queues attempt 1 and its job (`serialKey = conversationId`, kind send).
    - Idempotency key: `dispatch:quote:<versionId>:<channel>`. So "1 Approval" means the version's single approval row, carrying the payload hash.
  - **The quote PDF must exist before approve-and-send** (422 `QUOTE_PDF_NOT_READY`). The O3 hash binds `artifactSha256`, so the approver approves the rendered document. If the artifact disappears later, preflight retries `ARTIFACT_NOT_READY` (bounded by the job's attempts), and at the last attempt cancels `ARTIFACT_MISSING`.
  - **Messages without a quote.**
    - `createMessageDraft` creates a DRAFT Message with a PENDING OUTBOUND_MESSAGE approval (the approval-queue item).
    - `approveAndSendMessage` approves it as it stands (payload hash) and queues it. Idempotency key: `dispatch:message:<messageId>`.
    - `queueOutboundMessage(tx, ctx, {..., sendIntent, initiatedBy, dedupeKey})` is the entry for automated, bulk and customer-requested sends inside the caller's transaction (T21, T23). Idempotency key: `dispatch:outbound:<dedupeKey>`.
  - **Payload hash.** The hash covers `{channel, destinationKey, templateName, templateLang, variables, body, subject, attachment}` as canonical JSON (sorted keys).
    - `destinationKey` is the HMAC of the lead's current phone or email, so a contact edit after approval is APPROVAL_STALE.
    - Preflight recomputes the hash for every attempt that carries an approval. It also requires that approval to still be APPROVED (an INVALIDATED approval is stale).
  - **Preflight order:**
    1. Attempt state.
    2. Quote binding: version current and effective status APPROVED, SENT or VIEWED. Otherwise CANCELLED with `SUPERSEDED`, `QUOTE_EXPIRED` or `QUOTE_CANCELLED`.
    3. PDF present.
    4. Approval and its hash.
    5. T18 eligibility with the attempt's persisted intent and `initiatedBy`.
    6. Provider throttle window.
    7. SENDING.
  - **Preflight outcomes.**
    - Any non-deferrable reason: SKIPPED, with `reasonCode = reasons[0]` and every reason in `errorRedacted`.
    - Deferrals refund the attempt counter. Pauses recheck after 60 s; `CAP_REACHED` waits until the next local midnight of the workspace time zone.
    - In LIVE, a channel without a registered live transport is SKIPPED `NOT_CONFIGURED`. T32 and T33 add theirs in `defaultWhatsAppTransport` / `defaultEmailTransport` (`jobs/handlers/dispatch-run.ts`).
  - **Throttle window without a schema change.** A RETRYABLE failure with a throttle reason (`RATE_LIMITED`, `PROVIDER_QUOTA` workspace-wide; `PAIR_RATE_LIMITED` per conversation) requeues its job at `max(backoff, Retry-After)`. While that job is QUEUED with a future `runAt`, later preflights for the workspace (or the pair) defer to that `runAt` with `PROVIDER_THROTTLED`. No column was added: the window is the throttled job's own `runAt`.
  - **Pause points.** `dispatch.p1` follows the claim, before preflight. `dispatch.p2` follows the SENDING commit; a lease lost by then throws LeaseLostError, and the reaper makes the attempt AMBIGUOUS. `dispatch.p3` follows the provider call, before the settle. Preflight runs in a tenant-scoped transaction whose first statement after the write lock is `fenceJob`. The settle is the runner's fenced `finalTx`.
  - **Failure handling (E7).**
    - PERMANENT: the job SUCCEEDED (handled) and the Message FAILED. An error-map entry with `suppress` (131050) writes the suppression through `suppressContact`, with the journal exported by the reconcile job queued in the same transaction.
    - PRE_SEND and RETRYABLE: attempt N+1 (same job) while attempts remain. At the last attempt the job goes DEAD(MAX_ATTEMPTS) and the Message FAILED.
    - Ambiguous: a timeout after the write, an unconfirmed 5xx, or a transport that threw. The attempt is AMBIGUOUS, the Message UNKNOWN ("Delivery unknown"), and the job DEAD(AMBIGUOUS) with `retrySafe: false`.
    - The reaper's dispatch branch also sets the Message UNKNOWN.
  - **Settle.**
    - Lead stage moves forward only: CONTACTED, or QUOTE_SENT when a quote is attached.
    - Quote CAS (E6): on success, audit `quote.send` and set `sentVia = DISPATCH`. If the version was superseded, set that version's `sentAt` and audit `quote.sent_superseded_version`. If the same current version was already SENT by another channel, write no audit.
  - **Email fallback (plan §7).** A skipped WhatsApp send falls back to email only when all of these hold:
    - `emailFallbackEnabled` is on;
    - every skip reason is one email can answer (NO_WHATSAPP_OPT_IN, WINDOW_CLOSED, TEMPLATE_NOT_APPROVED, QUALITY_PAUSED, NOT_CONFIGURED; never pauses, opt-outs, takeover or a stale approval);
    - there is email content (a quote or a text body);
    - email is independently eligible for an AUTOMATED send.

    The fallback email is AUTOMATED with `initiatedBy = system:dispatch.fallback`. Refusals are audited as `dispatch.fallback_refused`.
  - **Unsubscribe link.**
    - Every email carries a signed token: `base64url(JSON {v, w, c}).HMAC`. The key is derived from SESSION_SECRET (`deriveUnsubscribeKey`).
    - The body links to `/unsubscribe/<token>`. The `List-Unsubscribe` header points to `/api/unsubscribe?token=...`, with `List-Unsubscribe-Post: List-Unsubscribe=One-Click`.
    - T20 verifies tokens with `verifyUnsubscribeToken`. The DEMO `from` address is `quotes@<slug>.invalid`; T33 replaces it from the integration's verified domain.
  - **DEMO transports and the tripwire.** The DEMO transports record each would-be send as one fsynced line in `<STORAGE_DIR>/demo-outbox/<channel>.jsonl`. A line holds the recipient's last four characters only. The provider id is `demo.wamid.<attemptId>` / `demo.email.<attemptId>`, labelled simulated. `adapters/http/outbound.ts` records every attempt and throws `OutboundBlockedInDemoError` in DEMO before any socket opens.
  - **ESLint rule `auralead/no-adapter-in-tx`** (local plugin in `eslint.config.mjs`, a T01 file, for `src/server/**` and `worker/**`; assigned to T19 by progress.md). Inside a callback passed to `withTx`, `fencedTx`, `$transaction`, `runSuppressionTx`, `withSuppressionTx` or `scopedFencedTx` it reports:
    - any value symbol imported from an `adapters/` module (type-only imports are allowed);
    - calls to `fetch`, to anything imported from `undici`, `http(s)`, `net`, `tls` or `dgram`, and to `safeFetch`.
- **Why:** The plan fixes the outbox contract and the test list but not these mechanics. T19 owns no route, and the schema has no throttle column.
- **Covered by:** `tests/integration/dispatch/{approve-and-send,payload-hash,version-binding,superseded-settle,retryable-rejection,auto-send-disabled-queued,lease-fencing-send}.test.ts`, `tests/integration/jobs/{lease-expiry-send,worker-restart,pause-honored}.test.ts`, `tests/integration/messaging/throttle-fallback-ambiguous.test.ts`, `tests/integration/security/outbound-tripwire.test.ts`, `tests/unit/messaging/error-map.test.ts`, `tests/unit/arch/tx-adapter-rule.test.ts`.
- **Reversibility:** 4.

### ADR-61 Bulk runs, the APPROVAL and DELIVERY stages, and resuming halted stages (T23)
- **Decision:**
  - **New `BulkRun` table (schema change, migration `20261016140000_bulk_runs`).** The plan asks for a "`bulk.run` job with persisted results" that survive a reload (06-design F19: "the result persists as a Job"), but `Job` has no result column and §5 has no home for per-row outcomes. Skipped rows must not create a DispatchAttempt (AT8), so their reasons cannot live on the outbox either.
    - One row per confirmed bulk action: `action` (SEND_WHATSAPP_TEMPLATE, SEND_EMAIL), `status` (QUEUED, RUNNING, COMPLETED), `requestKey` (UNIQUE per workspace), `params`, `leadIds`, `selectedCount`, `queuedCount`, `skippedCount`, `failedCount`, `results` (one entry per row, in selection order) and `preflight` (the counts shown when the run was confirmed).
    - `BulkRun` was added to `REQUIRED_TENANT_MODELS` in `src/server/db/scoped.ts`, and `Workspace` gained the `bulkRuns` back-relation.
  - **Bulk semantics.**
    - Every selected row is exactly one of three outcomes, so eligible (queued) + skipped + failed == selected:
      - FAILED: the action cannot apply to the row at all (`LEAD_NOT_FOUND`, `LEAD_MERGED`, `CONTACT_MISSING`).
      - SKIPPED: the shared eligibility function with sendIntent BULK reports a reason that cannot be deferred.
      - Eligible: no reason, or only deferrable ones (pauses, internal cap). A row with deferrable reasons is queued with `deferred: true`, and its dispatch waits.
    - The pre-flight writes nothing. The `bulk.run` job classifies every row again in fenced, tenant-scoped chunks of 25. Each chunk queues its rows through `queueOutboundMessage` (sendIntent BULK, `initiatedBy` = the confirming user, dedupe key `bulk:<runId>:<leadId>`) and persists their results in the same transaction, so a restart resumes after the last committed chunk.
    - Confirming a bulk send needs `approvals.decide` and `dispatch.send`; the confirmation is the approval. The pre-flight needs `dispatch.send`, and reading runs needs `leads.read`.
    - D4 is enforced by eligibility, not by a separate rule. Attested-B2B email is skipped `ATTESTED_MANUAL_ONLY`, and Maps leads have no WhatsApp opt-in (`NO_WHATSAPP_OPT_IN`).
    - Routes: `POST /api/app/bulk/preflight`; `POST` and `GET /api/app/bulk/runs`; `GET /api/app/bulk/runs/[runId]`. The workspace is chosen by `workspaceSlug`, as in the lead console routes (ADR-58).
  - **The first touch is what the pipeline approves and delivers.**
    - The APPROVAL stage takes the execution's AiDraft and builds the sendable options: a WhatsApp template message (needs the draft's approved FIRST_TOUCH template and a phone), then an email (needs a subject, a body and an address).
    - It checks each option with the shared eligibility function, using the intent the option would be sent with: MANUAL_SINGLE under HUMAN, AUTOMATED under POLICY_AUTO. It chooses the first option that is eligible or only deferred.
    - POLICY_AUTO approves by policy (`POLICY_APPROVED`, audited `pipeline.approval.policy`) only when all of these hold:
      - workspace auto-send is on now;
      - the draft is READY;
      - the draft has no AI policy flag, violation or escalation;
      - the chosen option is usable for an AUTOMATED send.
    - Otherwise, or under HUMAN, the stage creates the review item (`HUMAN_REVIEW`): a DRAFT outbound Message with a PENDING OUTBOUND_MESSAGE Approval flagged `pipeline_first_touch`, plus any `policy_auto_blocked:<reason>`.
    - With nothing sendable, the stage is SKIPPED: `NO_SENDABLE_DRAFT`, or `NO_DRAFT` when there is no draft.
    - DELIVERY queues the POLICY_APPROVED send with sendIntent AUTOMATED, `initiatedBy = system:pipeline.advance` and dedupe key `pipeline:<executionId>:DELIVERY`. It is SKIPPED `AWAITING_HUMAN_APPROVAL` for a review item and `NOTHING_APPROVED` when APPROVAL did not finish DONE.
    - The plan's "exactly one quote draft per lead" is read as one AiDraft (the draft bundle with the quote proposal) per execution. Turning the proposal into a Quote stays a person's action ("Create quote from proposal", ADR-58), because `createQuote` and `computeQuoteTotals` run their own transactions and cannot commit inside the fenced stage settle.
  - **Writes inside the stage settle.** The executor hands `finalTx` the raw transaction client, but `queueOutboundMessage` expects a tenant-scoped one. `scopeTransaction(tx, workspaceId)` in `stages/approval.ts` wraps the raw client in a Proxy that applies the scoped client's `scopeArgs` to every tenant model operation.
  - **Validator (P11).** The graph must meet all of these:
    - only the five fixed stage kinds, each at most once, with unique node ids;
    - edges only between known nodes, and no cycles;
    - INGESTION present, and every node reachable from it;
    - APPROVAL mandatory, and DELIVERY reachable only through APPROVAL;
    - stages in their fixed order, both per edge and in the executor's own `stageOrder`;
    - approval mode HUMAN or POLICY_AUTO, and POLICY_AUTO only while auto-send is on.

    Optional stages (SCORE, DELIVERY) may be left out. `savePipelineConfig` (`pipeline.manage`) validates the graph, applies a CAS on the active version (409 `PIPELINE_VERSION_CONFLICT`), activates version N+1 and audits `pipeline.config.activate`. An invalid graph is 422 `PIPELINE_INVALID` with the issues in `safeDetails`. T28's editor calls this service. T23 owns no pipeline route.
  - **Resuming halted stages.** `resumeHaltedStages` enqueues one `pipeline.advance` for each PENDING `STAGE_HANDLER_MISSING` run whose stage now has a handler. The key is `pipeline.advance:<executionId>:<stage>:resume:<runId>`, so repeated calls add nothing. `npm run pipeline:resume` (new `scripts/pipeline-resume.ts`, appended to `package.json` and the CLAUDE.md commands table) runs it once with the production stage registry. Nothing runs it automatically: the worker entry (T07) has no boot hook, and resuming is an operator decision after an upgrade.
  - **Files outside the Owns list:** `prisma/schema.prisma` and the migration, `src/server/db/scoped.ts` (the tenant model list), `src/lib/schemas/bulk.ts` (shared request schemas and DTOs), `src/app/api/app/bulk/_lib/deps.ts`, `scripts/pipeline-resume.ts`, and the appended shared files: job registry, stage registry, route manifest, the `bulk.unknownRunId` matrix fixture, `package.json` and CLAUDE.md.
- **Why:** The plan fixes the goals (bulk pre-flight with the shared eligibility function, persisted results, a validated graph, APPROVAL and DELIVERY on the pinned version, no auto-send of queued approvals) but does not say where results live or what the stages approve and send.
- **Covered by:** `tests/unit/pipeline/validator.test.ts`, `tests/integration/pipeline/{pinned-version,full-run-replay,resume-halted}.test.ts`, `tests/integration/bulk/bulk-actions.test.ts`, `tests/components/patterns/bulk-result-summary.test.tsx`, the tenant matrix (new manifest entries).
- **Reversibility:** 3 (table), 4 (the rest).

### ADR-62 WhatsApp and email webhooks, synchronous Stop, quick replies and statuses (T20)
- **Decision:**
  - **Raw-body routes.** `withRoute` parses every mutation body as JSON and does not expose the raw bytes, so signature-verified routes cannot use it. `src/app/api/webhooks/_lib/raw-route.ts` (new, shared, for T33-T36 too) reads the body once with the cap, gives the handler the raw bytes, runtime, request clock and correlation id, never reads cookies, and renders errors exactly like `withRoute`. `/api/webhooks/whatsapp`, `/api/webhooks/email/[provider]` and `/api/unsubscribe` use it.
  - **One WebhookEvent per item.** A WhatsApp delivery can carry several messages and statuses, so each is its own event: `wa:{msgId}` and `wa:{wamid}:{status}`, scoped by the routed integration (E2). `bodySha256` is the hash of the item's canonical JSON (the raw body covers the whole delivery). The inspector view (`payloadRedacted`) is built explicitly from ids, type and intent, never the phone or the text. A replay is a no-op; a same-key item with different content is reported `CONFLICT` and not stored (a 409 would make Meta retry forever). These events are written by `services/messaging/inbound.ts`, not T11's `persistWebhookEvent`: the Stop must share the insert's transaction, and T11's function owns its transaction and only enqueues `ingest.process`.
  - **Routing.** `Integration.routingKey` = `phone_number_id`, only for a `WHATSAPP_CLOUD` integration of a workspace in the process's mode; anything else is UNROUTED (no job, 30-day purge). Email events are routed by our own stored provider message id (`Message.channel = EMAIL`); scope key = workspace.
  - **Stop.** STOP keywords (fixed list incl. `बंद`, `बंद करें`, `रोकें`, `stop`, `unsubscribe`, `opt out`) match only the whole folded message (NFKC, case, spaces, trailing punctuation), so "which bus stop" is not a Stop. `AL_QR_STOP_V1`, or a quick reply whose button text is a Stop keyword whatever its payload, is `STOP_BUTTON`; text is `STOP_KEYWORD`. The route inserts the event, calls `suppressContact` (which cancels QUEUED and retry-waiting attempts, their jobs and messages) and enqueues `webhook.process` in one transaction, then flushes the journal. The job only records the inbound message for a known lead; a Stop from an unknown number never creates a lead and records no inbound consent.
  - **Inbound processing (`webhook.process`).** The sender is matched by LeadContactKey PHONE, falling back to `Lead.phoneE164` (hand-entered leads may have no key row), following merges. An unknown number becomes a lead through `ingestBatch` (source `WHATSAPP_INBOUND`, its own transactions, idempotent per message id; ADR-54 precedent). The inbound Message is stored once per provider id (kind TEXT, INTERACTIVE_REPLY or DOCUMENT; quick replies keep `{quickReply, payload, matchedBy}` in `variables`). The window moves only through `advanceLastInbound`; `unansweredOutboundCount` resets to 0 on inbound; the lead moves forward to REPLIED from NEW or CONTACTED. Every non-Stop inbound records INBOUND_MESSAGE / SERVICE_CONVERSATION consent (P13). START records the OPT_IN through `recordStartKeywordConsent`; its CLEAR journal line is exported by the reconcile job queued in the same transaction, because the job's transaction is not a `runSuppressionTx`.
  - **Quick replies.** The button-text fallback applies only when no payload was echoed. A present but unknown payload goes to review: the inbound message is stored, `quick_reply.review` is audited, and nothing automated happens (the schema has no review flag; T22's inbox shows the message).
    - QUOTE with an approved, live, rendered current quote queues the PDF as an in-window DOCUMENT reply (`CUSTOMER_REQUESTED_REPLY`, `initiatedBy = system:webhook.process`, no link). The version's APPROVED QUOTE_VERSION approval is bound to that message (payload hash) when it was never used for a send, exactly as approve-and-send binds it. Otherwise the reply is automated when auto-send is on, else a DRAFT with a PENDING approval flagged `customer_requested`.
    - QUOTE without one: the DRAFT quote's PENDING approval gets `customer_requested`. With no quote, the newest AiDraft with services becomes a DRAFT quote through `createQuoteFromProposal` (before the fenced transaction, in its own transactions; a re-run finds that DRAFT quote and creates none). With no usable proposal the result is `REVIEW_NO_PROPOSAL`. The holding message is one fixed text, sent only when auto-send is on.
    - CALL creates one CallRequest keyed `sourceEventId = WebhookEvent id`. An https booking URL (no credentials) becomes a reply: queued when auto-send is on, otherwise a DRAFT flagged `customer_requested, call_request`.
  - **Statuses (`status.apply`).** The pure merge is in `services/messaging/status-merge.ts` (new file). Positive ranks apply only upward; `failed` applies at rank <= 1 and pins the rank at 1 so a late `sent` cannot undo it; failed after delivered is an anomaly. There is one `MessageStatusEvent` per (providerMessageId, status); a stored event not yet linked to a message is applied when it correlates. An unknown id is `PENDING_CORRELATION` and the job retries with `retryAfterMs` 120 s, 6 attempts (5 retries, about 10 minutes), then ORPHAN. Each applied change is audited `message.status` (rank in the summary). An echoed `biz_opaque_callback_data` naming an AMBIGUOUS attempt resolves it to SENT (attempt `resolvedBy = system:status.apply`, message projection, lead stage, quote CAS), audited `dispatch.ambiguous_resolved`. Email: `email.sent` and `email.delivered` map to sent and delivered, a permanent `email.bounced` to failed; opens, temporary bounces, delays and complaints are stored only.
  - **Email webhooks.** `[provider] = demo` (DEMO process only) takes Resend-shaped events signed `x-auralead-signature: sha256=<HMAC(key, raw body)>` with `key = HMAC(SESSION_SECRET, "auralead.demo-email-webhook.v1")` (`demoEmailWebhookKey`), idempotency header `x-auralead-event-id`, provider enum `DEMO` (no real provider is behind it). A permanent bounce (`HARD_BOUNCE`) or a complaint (`COMPLAINT`) suppresses EMAIL synchronously in the route. `resend` answers 404 until T33 adds the Svix-verified receiver (nothing is ingested unverified); `smtp` answers 404 `EMAIL_PROVIDER_NO_WEBHOOKS` with the disclosure in `EMAIL_PROVIDER_CAPABILITIES`.
  - **Unsubscribe.** POST `?token=` with `List-Unsubscribe=One-Click` (RFC 8058) answers 200 JSON; POST with a form field `token` (the page's button) answers 303 to `/unsubscribe/<token>?done=1`; GET only redirects to the page, so link scanners never unsubscribe. Invalid, forged or other-mode tokens are 404 and write nothing. The token carries only the contact HMAC, so T18's `suppression.ts` gained `suppressContactKey` (additive; `suppressContact` now delegates to it). The plain address is stored only when an EMAIL conversation's lead proves it; otherwise the row is keyed by the HMAC alone. No WebhookEvent is written for an unsubscribe (it is not a provider event); the audit actor is PUBLIC.
  - **DEMO inbound simulation.** `POST /api/webhooks/whatsapp/simulate` (demo-only, USER/EMPLOYEE with `leads.write`, `workspaceSlug` resolved as in ADR-54) builds the Cloud API payload from the lead's own number (text, QUOTE, CALL, STOP, START) and runs the same receive path, routed to the workspace's WhatsApp integration (a SIMULATED one without routing key is created on first use), with events flagged simulated. It sits under T20's own `/api/webhooks/whatsapp/**` path, not T11's `/api/demo/simulate/[source]`.
  - **Rejections.** `services/webhooks/rejections.ts` (new, shared) increments the daily WebhookRejection counter (workspace null) for SIGNATURE_MISSING, SIGNATURE_INVALID, SECRET_NOT_CONFIGURED, INVALID_JSON and INVALID_PAYLOAD; nothing else is written for a rejected delivery.
  - **Files outside the Owns list:** `src/lib/schemas/webhooks/{whatsapp,email}.ts` (one schema set), `src/app/api/webhooks/_lib/raw-route.ts`, `src/server/services/webhooks/rejections.ts`, `src/server/services/messaging/{status-merge,unsubscribe}.ts`, the additive `suppressContactKey` in `suppression.ts`, and the append-only job registry and route manifest.
- **Why:** The plan fixes the behaviors (raw-body signature, routing, synchronous Stop, rank merge with orphan retry, quick-reply rules P3/P4, unsubscribe) but not these mechanics. `withRoute` cannot verify raw bytes, the unsubscribe token holds no plain address, and the schema has no review flag.
- **Covered by:** `tests/integration/webhooks/whatsapp-signature.test.ts`, `tests/integration/messaging/{stop-and-takeover,stop-with-worker-down,stop-race,quick-replies,window-dispatch,email-webhooks,inbound-simulation}.test.ts`, `tests/unit/messaging/rank-merge.test.ts`, `tests/integration/chaos/status-shuffle.test.ts`, the tenant matrix (new manifest entries).

### ADR-63 Conversations, takeover and the automated reply guard (T21)
- **Decision:**
  - **The reply guard writes no model text at all.** `services/ai/reply-guard.ts` classifies each inbound text into the seven plan intents with fixed, conservative rules (stop > complaint > human_request > call_request > quote_request > service_faq > out_of_scope). Anything it does not recognize is `out_of_scope`, so uncertainty escalates instead of being answered.
    - Complaint, human request and out of scope get one fixed deflection each.
    - Quote and call requests get fixed acknowledgements. The call acknowledgement may carry the https booking link (P4). Both escalate, because prices and call times come from a person.
    - A stop request inside longer text gets no reply and escalates. Whole-message Stops stay T20's synchronous path.
    - An in-scope FAQ answer is composed only from approved catalog facts: service name, description and typical timeline, never prices. The composed text runs through T14's output policy anyway, because the catalog is business-entered text. Any hit becomes the fixed handoff plus escalation (`OUTPUT_POLICY`). A workspace without a catalog cannot answer (`NO_APPROVED_FACTS`).
    - DEMO and LIVE behave the same and no provider is called. The plan says "no model free text" for the escalating intents. This ADR applies the stricter reading to FAQ answers as well, because the T14 AI port only implements the lead-draft task. A model-written FAQ answer would need a new port task, schema and contract fixtures, which is outside T21's ownership.
    - Replies carry `generatorLabel = 'reply-guard'`.
  - **Escalation = the thread goes back to a person.** An AUTO thread drops to DRAFT, with a compare-and-set bump of `modeVersion`, and the action is audited as `conversation.escalated` with the intent, reason and modes. A DRAFT thread only gets the audit plus the `escalated` approval flag.
    - In AUTO, the deflection or acknowledgement itself is queued AUTOMATED with the post-escalation mode version, so it passes check 5 and still goes through the whole preflight.
    - Escalation does not set `humanTakeover`. Takeover blocks automated sends, so it would also block the deflection the plan requires.
  - **Takeover is respected at dispatch, not by cancelling.** Takeover, resume, AI-mode changes and escalations all bump `modeVersion`. An automated reply pins `Message.modeVersionAtCreate`, so T18/T19's preflight skips it as `HUMAN_TAKEOVER` or `MODE_CHANGED` (plan §6.3 lists these as SKIPPED reasons). Takeover therefore does not cancel queued attempts. T22 can show a SKIPPED HUMAN_TAKEOVER reply as "AI reply cancelled by takeover" (06-design).
    - Mode changes take an optional `expectedModeVersion`; a stale value gives 409 `MODE_VERSION_CONFLICT`.
    - Takeover, resume and Off/Draft need `leads.write`.
    - AUTO also needs `automation.manage` and workspace auto-send on; otherwise 422 `AUTO_SEND_OFF`.
    - New threads start in DRAFT (schema default).
  - **A newer inbound supersedes a queued reply (T-b3) in two places.**
    1. `webhook.process` calls `afterInboundMessage` in its own transaction. For the newest inbound, it cancels the thread's QUEUED automated replies to older messages as `CANCELLED(NEWER_INBOUND)`, cancelling their jobs too (QUEUED jobs are cancelled, RUNNING jobs get `cancelRequestedAt`) and setting the messages NOT_SENT. For plain text in a DRAFT or AUTO thread without takeover, it enqueues `reply.auto` for this message (`reply.auto:<inboundMessageId>`, serialKey = conversationId).
    2. The reply job re-checks in its fenced transaction that its message is still `lastInboundMessageId`. If not, it audits `reply.superseded` and writes nothing.

    SQLite serializes the two write transactions, so a stale reply is either cancelled or never created. The dispatch preflight was not changed. An inbound with the same provider second as the previous one does not advance the window (T20's `advanceLastInbound`), so it is not "newest" and gets no reply of its own.
  - **AUTO replies use the outbox.** They are queued through `queueOutboundMessage` with `sendIntent = AUTOMATED`, `initiatedBy = system:reply.auto` and dedupe key `reply:<inboundMessageId>`, with `replyToInboundId` and `modeVersionAtCreate` set in the same transaction. Before queueing, the job runs the shared eligibility function for AUTOMATED:
    - eligible or deferrable: the reply is queued;
    - blocked only by automation reasons (auto-send off, quality RED, takeover, mode change, workspace pause): a DRAFT plus a PENDING `OUTBOUND_MESSAGE` approval flagged `ai_reply`, `intent:<x>` and `auto_blocked:<reason>`, so a person can still send it ("quality RED pauses automation only");
    - anything else: no message, audited `reply.skipped`.

    DRAFT threads always produce the draft and approval, unless a manual send would be refused too. Replies are WhatsApp-only, because there is no inbound email path.
  - **Workspace auto-send toggle.** `setWorkspaceAutoSend(ctx, {enabled})` needs `automation.manage`. It sets `updatedBy` and audits `workspace.auto_send {enabled, previous}`; a repeat is a no-op with no audit. Plan §5 has no owner for this toggle, and R29 needs it audited. Turning it off stops queued automated work at dispatch (`AUTO_SEND_DISABLED`), and an AUTO thread's next reply becomes a draft.
  - **`unansweredOutboundCount`** grows by one when an attempt actually moves SENDING to SENT. That covers two places: T19's `settleSent`, and T20's AMBIGUOUS resolution by a status echo. T20 already resets it on every inbound. No cap is enforced.
  - **Edits outside the Owns list (additive):**
    - `services/messaging/inbound.ts`: the `afterInboundMessage` call, and the increment on AMBIGUOUS resolution.
    - `services/messaging/dispatch.ts`: the increment in `settleSent`.
    - `tests/integration/messaging/inbound-support.ts`: the harness also runs `reply.auto`.
    - Append-only shared files: the job registry.
    - New test support: `tests/integration/messaging/conversation-support.ts`.
    - No routes: `/api/app/conversations/**` belongs to T22, which wraps these services.
- **Why:** The plan fixes the intents, takeover at dispatch, `modeVersion` and the escalation duty, but not what escalation does to the thread, where the toggle lives, how a newer inbound reaches a queued reply, or who increments the unanswered count.
- **Covered by:** `tests/unit/ai/reply-guard.test.ts`, `tests/integration/messaging/{takeover-race,auto-send-audit}.test.ts`, `tests/integration/ai/auto-reply-guard.test.ts`.
- **Reversibility:** 4.

### ADR-64 Admin inspector, fresh authentication, global pause, backup/restore and lead erasure (T24)
- **Decision:**
  - **Fresh authentication instead of `withRoute({ reauth: true })`.** The admin mutations (`/api/admin/jobs/[jobId]/{cancel,retry,resolve}`, `/api/admin/system/outbound-pause`) call `requireFreshAuthentication` (`services/admin/fresh-auth.ts`): a password re-entry (`Session.reauthAt`) or the sign-in that created the session (`Session.createdAt`) within 15 minutes. In LIVE every session is created by a password sign-in or a re-auth, so this is still "a password entry within 15 minutes" (plan §9). In DEMO the seeded personas have no password, so `reauthAt` can never be set; the persona sign-in is their authentication, and the dialog offers "Sign in again as Super admin". Without this the DEMO global pause and inspector would be unusable. A stale session answers 401 `REAUTH_REQUIRED`; the dialog re-authenticates in place and retries with the new CSRF token.
  - **Inspector reads are platform metadata, not a drilldown.** Job lists, redacted payloads (ids only, run through `redact()` again), attempt logs, dispatch attempt states, audit action names in the correlation timeline, and webhook `payloadRedacted` / `result` are shown without `adminContext`. The encrypted processing payload is never decrypted. Every inspector action runs under `adminContext(ctx, job.workspaceId, reason)` (an `admin.elevate` row first) and writes its own `job.cancel` / `job.retry` / `dispatch.operator_resolve` row with `crossWorkspace` and the reason. System jobs (no workspace) are audited the same way without the elevate row.
  - **Safe retry (plan §6.2 "only when retrySafe or the linked attempt was resolved by an operator").** No producer sets `Job.retrySafe`, so the rule is applied by job type: a DEAD job without provider side effects (every type except `dispatch.*`; their writes are fenced and idempotent by key) is requeued as is (attempts reset, same job). A DEAD dispatch job never resends blindly: an unresolved AMBIGUOUS attempt answers 409 `AMBIGUOUS_UNRESOLVED`; otherwise attempt N+1 is created on a NEW job (key `dispatch:operator-retry:<sourceAttemptId>`, intent and initiator copied, E4) only when the last attempt definitely did not send (FAILED PRE_SEND/RETRYABLE, or resolved "not delivered" by an operator). The new job re-runs the full preflight, so a suppressed lead is skipped (SUPPRESSED) or cancelled by a later Stop.
  - **AMBIGUOUS resolution.** "Mark delivered" sets the attempt SENT (no provider id), the message SENT, the lead stage and quote CAS exactly as a settle (E6). "Verified not delivered" sets FAILED (`OPERATOR_NOT_DELIVERED`); with `requeue` it needs the typed confirm text `RESEND` (422 `CONFIRMATION_REQUIRED`). `resolvedBy`, `resolvedAt` and the reason (`resolutionNote`) are stored.
  - **Restore copies rows into the live file in one transaction** instead of swapping the file: `ATTACH` the backup, delete every application table, `INSERT ... SELECT` the common columns, reconcile, replay, pause, audit, commit. No Windows file locks, no half-restored state, and a backup taken before a later additive migration still restores; a backup with migrations this DB lacks is refused. `WorkerHeartbeat` and `_prisma_migrations` are live state and are kept. Pre-backup QUEUED or SENDING attempts become AMBIGUOUS (`RESTORED_IN_FLIGHT`), their jobs DEAD(AMBIGUOUS), their messages UNKNOWN. Journal entries newer than `backupAt` are replayed in event order (STOP before CLEAR at equal times), idempotently by suppression id; each applied entry is audited `suppression.replay`. A fresh worker heartbeat refuses the restore (`--allow-running-worker` overrides). Checks that need no DB change (manifest, mode, sha256, worker) run before the lock; the lock is then written first, and removed again only if the transaction did not commit and the lock did not exist before.
  - **The pause after a restore.** Both the lock (`writtenBy: db:restore`) and `SystemSetting.outboundPaused` (by `system:db.restore`) hold it. Resuming in the admin panel clears the DB flag and removes a restore-written lock; a hand-made lock is reported and left alone, and `OUTBOUND_PAUSED=1` needs a restart.
  - **Backup format.** `VACUUM INTO <BACKUP_DIR>/auralead-<mode>-<UTC stamp>.db` (written as `.partial`, renamed), then `<file>.json` with `{format: 1, mode, backupAt, file, bytes, sha256, migrations}`; `backupAt` is taken before the copy starts. `ops.backup` and `ops.restore` are audited.
  - **Lead erasure deletes, not anonymizes.** The lead, every lead merged into it, and every row carrying their data are deleted in one transaction with deferred foreign keys (a missed reference fails the commit); quote PDF files are removed after commit; matching webhook events lose their processing payload and inspector view; the person's queued jobs are cancelled. Suppression rows and their contact HMAC stay with `contactPlain` nulled. A `lead.erase` tombstone holds counts and the reason only. Refused with 409 `ERASE_SEND_IN_FLIGHT` while a send is SENDING.
  - **Files outside the Owns list:** `src/lib/schemas/admin.ts` (one schema set), the services `services/admin/{fresh-auth,outbound-pause,backup,lead-erase,webhook-inspector}.ts` (admin/** is owned; these are the inspector, pause and ops parts), the appended route manifest entries, `MATRIX_FIXTURES` keys `admin.unknownJobId` / `admin.unknownEventId`, the admin nav items "Jobs and queue" and "Webhooks", `package.json` scripts `db:backup`, `db:restore`, `lead:erase`, and the CLAUDE.md commands table.
  - **Not done here:** the P20 T24 part (re-basing window fixtures in `demo:refresh`): no task seeds conversation or window fixtures, so there is nothing to add to `REBASE_COLUMNS` yet.
- **Why:** The plan fixes the behaviors (no blind resend, typed reasons, re-auth for the pause, lock first, AMBIGUOUS reconcile, journal replay, PII removal with the suppression key kept) but not these mechanics; DEMO has no password to re-enter, and `Job.retrySafe` has no producer.
- **Covered by:** `tests/integration/admin/{inspector-actions,inspector-reads,queue-health,global-pause}.test.ts`, `tests/integration/ops/{restore-reconcile,lead-erase}.test.ts`, the tenant matrix (new manifest entries).
- **Reversibility:** 4.

### ADR-66 UI v2 "Aurora": colorful, animated, cinematic redesign (owner request, 2026-10-20)
- **Decision:** The owner asked for a far more colorful, punchy and cinematic UI with more animation, built from the best prebuilt components (three.js, shadcn, Skiper UI and similar). The redesign keeps every product rule that carries meaning and amends only the visual rules of plan §10 and 06-design §11.7-11.8:
  - **Palette v2 "Aurora"** (`src/styles/tokens.css`): blue-tinted surfaces; `--text-3` raised so it passes on `bg-3` (4.40:1 became 5.68:1); a solid `--border-input` that meets WCAG 1.4.11 (1.57:1 became 3.33:1); brand hues aura (action, links, focus, Client panel), azure (button gradient end only), volt / volt-hi (decorative fills and gradient stops only), flare (Platform admin, sparks), zest (Operator panel, sparks), ice; status chroma lifted, and danger moved from hue 22 to 28 so it clears flare. Buttons, links and focus stay aura everywhere. Gradients never put blue next to pink, and ice to flare interpolates in oklab, so no gradient crosses the reserved AI violet. Contrast is proven by `tests/unit/design/contrast.test.ts`.
  - **Gradient text** in panels: the one page `h1` per view (through `PageHeader`), the auth wordmark, the decorative 404 numeral and the landing hero keyword. Never on numbers, body copy or tables.
  - **Ambient motion in panels**:
    - Loops: the page-header aurora drift plus at most one comet border or border beam per view. Loops animate transform or opacity only and pause offscreen and in hidden tabs.

### ADR-67 Password reset by single-use link, issued by an administrator or the operator (owner request: production-ready LIVE)
- **Decision:**
  - New table `PasswordReset` (migration `20261020100000_password_reset`): `tokenHash` (sha256 of a 32-byte token), `userId`, `createdBy`, `expiresAt` one hour after creation, `usedAt`. It is platform-wide identity data, so it sits on the `IDENTITY_ALLOWLIST` of the tenant-column test next to `Session`.
  - `server/auth/password-reset.ts`: `createPasswordReset` (a newer token ends every earlier unused token of the user), `issuePasswordReset` (one transaction with the `password.reset_issue` audit event, used by the admin People page and the CLI), `redeemPasswordReset` (conditional update so two concurrent redemptions cannot both win; sets the password, clears `failedLoginCount` and `lockedUntil`, revokes every session, audits `password.reset`).
  - `POST /api/app/auth/reset { token, password }` and the page `/reset/[token]`. Unknown, expired, used, superseded, disabled-user and demo-in-LIVE tokens are one 404; the password policy is checked only after the token, so an unknown token never reveals anything. No cookie is set: the person signs in with the new password, so a leaked link alone never yields a session. Rate limit: `inviteReset` (10/h) per IP, Origin-checked.
  - There is no self-service "forgot password" email. The platform has no email transport of its own (providers are per-workspace integrations, plan §9), and a reset mail sent through a customer's integration would leak one tenant's brand and quota into another's account recovery. Recovery is therefore administrator-assisted; this is a stated limitation, like MFA.
- **Why:** The plan (T29) lists "reset links" under People but defines no mechanism; LIVE had no way to recover a password at all.
- **Alternatives:** reuse `Invite` for resets (rejected: an invite creates or joins, a reset changes a secret and must revoke sessions); sign the token with HMAC and store nothing (rejected: cannot be single-use or superseded without state); auto-login after a reset (rejected: a leaked link would yield a session).
- **Covered by:** `tests/integration/auth/password-reset.test.ts`, the tenant matrix (new manifest entries), `tests/unit/arch/tenant-columns.test.ts`.
- **Reversibility:** 4.

### ADR-68 First-administrator bootstrap for LIVE: `npm run admin:bootstrap`
- **Decision:** `scripts/admin-bootstrap.ts` over `server/auth/bootstrap.ts`. While no active, non-demo `SUPER_ADMIN` exists it creates a platform `Invite` (role SUPER_ADMIN, no workspace, `createdBy = system:operator`, 72 h) and prints `<APP_ORIGIN>/invite/<token>`; the person chooses their own name and password in the browser, so the CLI never handles a password and the existing, tested invite redemption path creates the account. Once an administrator exists it refuses with the hint to invite people from Admin > People; `--recover --email <admin>` then prints a one-hour reset link (ADR-67) for that existing administrator, which is the lost-password break-glass for someone with shell access. It refuses in DEMO, for an email that belongs to a non-admin, and retires an earlier unredeemed bootstrap invite for the same email. The link is printed to the terminal only; the audit rows (`admin.bootstrap`, `password.reset_issue`, actor kind SYSTEM) never contain it.
- **Why:** A fresh LIVE database has no users, `/login` says accounts are created by invitation, and invites need an administrator: LIVE could not be entered at all. Shell access to the server is the trust anchor for the first account.
- **Alternatives:** an environment variable with the first admin's password (rejected: secrets in env files and shell history); an unauthenticated first-run setup page (rejected: whoever reaches a new deployment first would own it); a `--password-stdin` mode (not needed: the invite flow already sets a password safely).
- **Covered by:** `tests/integration/auth/admin-bootstrap.test.ts`, `tests/integration/ops/admin-bootstrap-cli.test.ts`.

### ADR-69 `src/proxy.ts`: nonce CSP, HSTS and request id on every HTML response
- **Decision:** `src/proxy.ts` (Node runtime, plan §3) sets, per request, a CSP with a fresh script nonce plus `strict-dynamic` (no `unsafe-inline` or `unsafe-eval` script in production; `unsafe-eval` and websockets in development only), `default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, same-origin connections, `img-src 'self' data: blob:` and `worker-src 'self' blob:` for the 3D aura and logos; `Strict-Transport-Security` and `upgrade-insecure-requests` only when `APP_ORIGIN` is HTTPS (so LIVE over plain `http://localhost` keeps working and a real deployment gets HSTS); and `x-request-id` on pages. Styles keep `'unsafe-inline'` because React and the motion library write `style` attributes, which a nonce cannot cover. The matcher skips `/api/*` (JSON), `/quote/*` (the public quote page already sets its own hash-based CSP, ADR-57), static assets and prefetches. The proxy still never authorizes, rate-limits or reads the DB. Builders live in `src/lib/security-headers.ts` so the policy is unit-tested without a browser.
- **Why:** Plan §9 (XSS) requires a nonce CSP and `src/proxy.ts`; neither existed, and a production deployment needs them. Nonces require dynamic rendering of every HTML page; all pages are already `force-dynamic` because they read the session or the mode.
- **Alternatives:** a static CSP in `next.config.ts` with `unsafe-inline` scripts (rejected: defeats the purpose); hashes for Next's inline bootstrap (rejected: they change per build and per page).
- **Covered by:** `tests/unit/security/security-headers.test.ts`, the browser check recorded in `docs/progress.md` (built LIVE app, no CSP violations, login and hydration working).
- **Reversibility:** 4.

### ADR-75 Metrics, command centers and productivity details (T25)
- **Decision:**
  - **One read model per dashboard, one aggregate per widget.** `services/metrics/` holds `widget.ts` (the `MetricDefinition` shape, `settleWidget`, money as `{paise: bigint, count}`), `definitions.ts` (every label and definition string, plus the Prisma filters that implement them), `command-center.ts` (`loadClientCommandCenter`), `platform.ts` (`loadPlatformMetrics`) and `productivity.ts` (`loadProductivity`). The client loader reads through the tenant-scoped client; the admin loader groups the same filters by workspace, so a workspace's row in the admin table always equals its owner's command center.
  - **Definitions.** Pipeline value = current-version totals of SENT and VIEWED quotes with `validUntil > now` (a SENT/VIEWED quote past its validity reads EXPIRED before the sweep runs, exactly as `effectiveQuoteStatus`, and is excluded with CANCELLED and EXPIRED). Accepted quote value = the accepted versions of ACCEPTED quotes. Confirmed revenue is always "Unavailable, No payment data" (O6, ADR-28). Quotes awaiting approval = quotes in DRAFT. New leads = created in the last 7 days; merged duplicates never count anywhere. "Needs you" = pending quote and message approvals, quote approvals withdrawn in the last 7 days by an edit after they were approved (`INVALIDATED`, `QUOTE_REVISED`, `decidedAt` set), outbound messages FAILED in the last 7 days, UNKNOWN deliveries (no time limit: they wait for an operator), open threads under human takeover and OPEN call requests.

Numbers never tick or poll; "As of" plus Refresh is the only way they change.
  - **Query budget (plan "under 15 queries per dashboard load").** Counted as SQL statements at the driver adapter (a counting wrapper around `PrismaBetterSqlite3`), for the dashboard's read model after the context is built: client command center 12, admin global metrics 13 (platform health, accounts, totals and the whole workspace table), productivity 8. Every per-workspace or per-employee figure is one grouped statement, so the count does not grow with rows or workspaces.
  - **Admin aggregates are not a drilldown.** Counts and sums per workspace are platform metadata (the ADR-64 inspector precedent): no tenant record is read or shown, so no `admin.elevate` row is written. Opening a workspace's records stays T29's audited `adminContext`. The admin home now reads `loadPlatformMetrics`, which also returns the worker, outbound pause (through `readOutboundPause`, as Jobs and queue) and account counts; `loadAdminHome` in `shell/panel-home.ts` (T09) is left unchanged for its own test but no page calls it any more.

Only SUCCESS rows count. Deviation from "all metrics from AuditEvent": an audit row carries no request time, so the median uses the `requestedAt` of the Approval row the decision's audit entry names (`summary.approvalId` of quote.approve, the target of approval.reject); decisions that name no approval are counted but not timed, and the page shows how many decisions the median is based on.

  - **Command center content.** The T09 home (catalog, active configuration, pipeline stages, terms, team) is replaced by the KPI row, "Needs you", leads by sales stage and recent activity; those settings live on Pricing. The funnel is CSS bars with the count and share in text (no chart library, nothing animated). The activity feed shows plain-language labels for every audit action (`components/metrics/activity-vocabulary.ts`), links quotations and conversations, and never renders an audit summary.
  - **Files outside the Owns list:** `tests/integration/shell/user-home-page.test.ts` (rewritten for the new home), `tests/e2e/smoke/shell.spec.ts` (the user-home assertions now check the KPI labels and "As of" instead of the removed catalog), the manifest entry for `/dashboard/admin/productivity`, and the admin nav item "Productivity".
- **Why:** The plan fixes the widgets, O6 labels, P10 metrics and the query budget, but not where definitions live, how a partial failure renders, what counts as a "query", or how the median gets a request time.

### ADR-76 Branding, logo upload and quotations list polish details (T27)
- **Decision:**
  - **Branding is its own page in the Pricing area.** `/dashboard/user/pricing/branding` (linked from the Pricing header) holds the logo, the brand colour and the sender details (GSTIN, terms). Changes need `pricing.override`, as all pricing changes do (ADR-52); members see the same details read-only with each save gated by permission. Routes: `POST /api/app/branding` (partial `{brandColor?, gstin?, termsText?}`), `GET` and `POST /api/app/branding/logo`, `POST /api/app/branding/logo/remove`, all role USER on the session's workspace. Audits: `branding.update` (field names only), `branding.logo.update` (type, sizes and dimensions, never the file name), `branding.logo.remove`. The GSTIN can also still be edited on the Tax tab (T13); both paths use the same `GSTIN_PATTERN`.
  - **Logo upload transport.** `withRoute` parses every body as JSON, so the logo travels as `{contentType, fileName?, dataBase64}` instead of multipart or raw bytes; the route's body cap is the base64 size of 1 MB plus 64 KB, and the decoded file is capped at 1 MB again in the service. Either limit answers 413 (`PAYLOAD_TOO_LARGE` from the body reader, `LOGO_TOO_LARGE` from the service).
  - **Logo checks (P7).** The declared type must be PNG, JPEG or WebP (`LOGO_TYPE_UNSUPPORTED`, so SVG is refused); the magic bytes, the file name's extension (when given) and the format sharp decodes must all equal the declared type (`LOGO_TYPE_MISMATCH`); undecodable bytes are `LOGO_UNREADABLE`; a decode is limited to 25 megapixels (`LOGO_DIMENSIONS`). The image is auto-oriented, fitted inside 512 px and re-encoded to WebP, and sharp writes no metadata unless asked, so EXIF/ICC/XMP and anything appended to the source are dropped; the stored bytes are never the uploaded bytes, which also defeats polyglots that pass the magic-byte check.
  - **Logo storage.** `STORAGE_DIR/branding/<workspaceId>/<sha256>.webp` (temp file + rename) is written before the transaction that records `WorkspaceSettings.logoPath`; a failed transaction deletes the new file unless it already was the current logo, and the replaced or removed file is deleted after commit. Reads accept only a path of exactly that shape for the caller's workspace and check the bytes against the hash in the name (500 `LOGO_INTEGRITY` otherwise). The served logo has a fixed `image/webp` type, `nosniff`, `inline` disposition, `Content-Security-Policy: default-src 'none'; sandbox`, an ETag of the hash and `no-store` (withRoute).
  - **The logo is not printed on quotations.** Neither the PDF nor the public quote page has a logo hook, and react-pdf cannot embed WebP; adding one would change the render model, its content hash and both presenters, which this task was asked not to rewrite. The branding page says so plainly ("Quotation pages and PDFs show your business name, brand colour and GSTIN; they do not print the logo"). Follow-up: a `logoSha256` in `QuoteVersion.snapshot.document`, a PNG rendition for the PDF and a token-gated public logo route.
  - **F14 brand colour as text.** `src/lib/branding/contrast.ts` (`brandTextColor`) darkens the brand colour in OKLCH, keeping hue and lowering lightness as little as needed (chroma reduced only to stay in sRGB gamut), until the rounded hex reaches the target contrast. The public quote palette (`components/quote/brand-palette.ts`, its existing branding hook) now takes its `text` colour from it, at its own stricter 4.6:1 on the wash tint, instead of an sRGB mix towards black; this is the only change to the quote presenters. The branding page previews with the same palette, so the colour and ratio it shows are what quotations paint. The stored brand colour stays the workspace's choice (`#RRGGBB` upper-case); brand colours in the preview are user data set through CSS custom properties, not design tokens.
  - **Terms.** Line endings normalised to `\n`, trailing spaces trimmed, at most 4000 characters (`TERMS_INVALID`); an empty value is allowed (quotations then print no terms).
  - **Quotations list filters.** `services/quotes/list.ts` (new; T15's `listQuotes` and its API route are unchanged): status by the status a reader sees (an APPROVED/SENT/VIEWED quote past `validUntil` is found under Expired), search over the quote number and `Lead.nameNormalized` (`normalizeName`, so case and accents fold), and "needs pricing review". The page uses a plain GET form (`?q=&status=&review=1`), status chips that link to their filter, counts over every quotation matching the search (two grouped statements) and a "No quotations match" state with Clear filters. The "Needs you" links from the command center (`?status=DRAFT`) land here.
  - **Status history.** The quotation detail page gains a "Status history" card above the timeline: one step per status change derived from the same audit rows (create/revise Draft, approve, send, view, accept, expire, cancel; repeats collapsed), with who, version and time in each status; a quote past its validity before the sweep shows a derived Expired step at its validity date.
  - **Files outside the Owns list:** `src/lib/branding/contrast.ts` and `src/lib/schemas/branding.ts` (pure and shared by the service, routes and client forms, the one-schema-set rule), `src/components/quote/brand-palette.ts` (one line, above), `src/app/dashboard/user/pricing/page.tsx` (the Branding link), `src/app/dashboard/user/quotations/{page.tsx,[quoteId]/page.tsx,status-history.tsx}` and `src/server/services/quotes/list.ts` (the list filters and status history the T27 goal names), and the route manifest entries (one page, three routes).
- **Why:** The plan fixes P7, F14, the GSTIN format and "filters and status history polish", but not the upload transport inside `withRoute`, where the logo is used, or how the list filters treat effective expiry.
- **Covered by:** `tests/integration/branding/{logo-upload,branding-settings}.test.ts`, `tests/unit/branding/contrast.test.ts`, `tests/components/pricing/branding-forms.test.tsx`, `tests/integration/quotes/list-filters.test.ts`, `tests/unit/quotes/status-history.test.ts`, the tenant matrix (new entries).

### ADR-70 Lead CSV exports: a LeadExport table, a job, 24 hours, requester-only downloads (T26)
- **Decision:**
  - **New `LeadExport` table (schema change, migration `20261020300000_lead_exports`).** The plan asks for an export "job (audited, expires 24 h)", but a Job has no result column and §5 has no home for the file, its hash or its expiry (ADR-61 precedent). One row per request: `requestKey` (UNIQUE per workspace, so a double click is one export), `status` (QUEUED, READY, FAILED, EXPIRED), the list `filters`, `requestedBy`, `rowCount`, `truncated`, the file's relative `path`, `sha256` and `bytes`, `completedAt`, `expiresAt`, `purgedAt` and the download count. `LeadExport` joined `REQUIRED_TENANT_MODELS`.
  - **Request.** `POST /api/app/leads/exports` (`leads.export`; among members only the OWNER holds it) stores the row, enqueues `leads.export` (key `leads.export:<exportId>`) and audits `lead.export.request` in one transaction. The audit names the filters (stage, source, score band, sort) and whether a search was used, never the search text, which can be a name or a phone number.
  - **Job.** `leads.export` walks the matching leads with the list's own filters and keyset order (merged leads left out), writes `STORAGE_DIR/exports/<workspaceId>/<exportId>.csv` (temp file and rename) outside any transaction, then in the fenced settle marks the export READY, sets `expiresAt = completedAt + 24 h`, audits `lead.export.ready` and enqueues `leads.exportPurge` with `runAt = expiresAt`. A write failure retries with backoff; the last attempt marks the export FAILED. The purge job deletes the file and marks it EXPIRED (audited `lead.export.expire`); run early, it defers to the expiry. The file is capped at 50,000 rows (`truncated` says so).
  - **Download.** `GET /api/app/leads/exports/[exportId]/download`: only the person who requested the export (anyone else, the owner included, gets 404), only while READY and before `expiresAt` (410 `EXPORT_EXPIRED` from that instant, even before the purge ran; 409 while preparing), only when the file still matches its sha256 (500 otherwise). Each download is audited `lead.export.download`. The response is a `text/csv; charset=utf-8` attachment with nosniff, no-referrer and no-store.
  - **CSV format** (`services/leads/csv.ts`). RFC 4180 with CRLF rows and a UTF-8 BOM (spreadsheet apps then read Devanagari and the rupee sign correctly). Every text cell starting with `= + - @ TAB CR` gets a leading apostrophe (plan §9), which includes E.164 phones (`'+9198...`): that is the documented cost of the rule. Numbers stay numbers. Labels are the panel's vocabulary (a component test keeps them in step).
  - **Lead erasure ends exports (edit to T24's `lead-erase.ts`).** A READY export written before an erasure may hold the person's row, so `eraseLead` marks every READY export of the workspace EXPIRED (`LEAD_ERASED`) in its transaction and deletes the files after the commit, like the PDFs. Its result gained `exportsExpired`.
- **Why:** The plan fixes the behaviour (audited job, 24-hour expiry, formula escaping) but not where the file lives, who may fetch it, or how an expiry is enforced. Requester-only downloads keep a bulk copy of contact data with the one person who asked for it.
- **Covered by:** `tests/unit/export/csv.test.ts`, `tests/integration/leads/export-job.test.ts`, `tests/components/leads/scoring-and-export.test.tsx`, `tests/components/leads/lead-detail-parts.test.tsx` (label sync), the tenant matrix (new manifest entries), `tests/e2e/user/leads.spec.ts` (export download).
- **Reversibility:** 3 (table), 4 (the rest).

### ADR-72 Leads area mechanics: URL state, normalized search, keyset pages, stage CAS, consent display, scoring tab (T26)
- **Decision:**
  - **Everything is in the URL.** `?q=&stage=&source=&score=&sort=&cursor=&dir=&view=&lead=` (`src/lib/schemas/leads.ts`, parsed leniently: an invalid value is dropped, a cursor that no longer decodes shows the first page with a note). Reload, the back button and shared links show the same rows. The toolbar is a GET form (works without JavaScript); with JavaScript a changed select navigates in place.
  - **Search runs on the normalized columns** (plan §5.8). The query goes through the same `normalizeName` that ingestion stores in `nameNormalized`, so case, accents and punctuation fold the same way on both sides; Devanagari folds too (vowel signs are combining marks, removed on both sides, so `शर्मा` finds `राहुल शर्मा`). Three or more digits (Devanagari digits read as 0-9) search `phoneE164`; a fragment of address characters searches `emailNormalized`. Only letters, digits and `@ . + -` reach a `LIKE`, so `%` and `_` never act as wildcards; a query with nothing searchable matches nothing.
  - **Keyset pages of 50** over a total order (sort key, then id) for the four sorts (newest, oldest, score with unscored leads last in both directions, name), forward with `cursor` and backward with `dir=prev`. Counts use `count({ take: 1001 })` and read "1,000+" past the cap. Merged leads are never listed. The board lists each stage's first 30 cards in the chosen sort with a capped count per column and ignores a stage filter.
  - **Stage moves** (`services/leads/stage.ts`, `POST /api/app/leads/[leadId]/stage`, `leads.write`). A compare-and-set on `stageVersion`: a stale version is 409 `STAGE_VERSION_CONFLICT` with the current stage and version; the UI then says so and re-reads instead of moving the card. People may move a lead in any direction (reopening a lost lead too); LOST needs a reason of at least 3 characters (422 `LOST_REASON_REQUIRED`) kept on the audit row; a move to the current stage is a no-op without audit; a merged lead is 422 `LEAD_MERGED`. Every move is audited `lead.stage` with from, to and the new version. The table, the board's "Move to stage" menu (the keyboard path), drag and drop on the board, and the detail views all use this one request.
  - **Automatic promotions bump the version too.** The dispatch settle, inbound replies and "mark sent" already moved forward only and incremented `stageVersion`; quote acceptance (T16's `accept.ts`) moved the lead to CONVERTED without the increment, so an open board could overwrite a conversion. It now increments it (one-line edit).
  - **Detail.** `services/leads/profile.ts` reads one lead for the client panel's sheet (`?lead=`, so a reload reopens it), the client panel's lead page and the operator console's lead page: the stage with its version, the stored score breakdown, consent per channel matched by the contact HMAC exactly like eligibility (an active opt-out first, then an opt-in, an attested B2B email basis or the customer's own message; display only, dispatch re-checks), the source records with attribution and batch (never the raw payload), quotations and conversations. The sheet is a Radix portal, so it is absent from server markup; its "Open full page" link and the lead page carry the same content.
  - **Components.** `ScoreBreakdown` and `ConsentChips` (listed under `components/patterns` in plan §3) live in `src/components/leads/`, which T26 owns.
  - **Routes and roles.** Stage and export routes are USER and EMPLOYEE, the workspace chosen by `workspaceSlug` as the lead console routes (ADR-58). The scoring routes `POST /api/app/scoring/{preview,versions}` are EMPLOYEE only.
  - **Scoring tab (P9).** Operators with `scoring.manage` edit; the workspace owner reads only: the service refuses preview and activation unless the actor is an EMPLOYEE with the capability (403 `SCORING_READ_ONLY`), because an OWNER otherwise holds every capability in their workspace (§5.2). Validation is the shared Zod schema (400 `SCORING_CONFIG_INVALID` with the issues). Preview scores the 20 newest unmerged leads with the pure scorer and writes nothing. Activation is one transaction: CAS on the active version the editor saw (409 `SCORING_VERSION_CONFLICT`), the old version deactivated, version N+1 created active, `lead.rescore` enqueued (ADR-53's key `lead.rescore:<versionId>`) and audited `scoring.config.activate`. Going back to an older configuration loads its weights into the form and activates them as a new version, so stored versions are never edited and every activation gets its own rescore. The client panel gets a read-only scoring tab (`/dashboard/user/leads/scoring`).
  - **Bulk selection in the operator console** (PRD: "lead console with bulk selection + eligible/skipped counts"; T23 built the routes and the result drawer but no screen used them). The console's table gains a checkbox column (TanStack row selection keyed by lead id, so it survives paging) and a "Bulk send" action, gated by `dispatch.send` and `approvals.decide` (the confirmation is the approval, ADR-61). The dialog takes an email (subject, body) or an approved WhatsApp template (configuration gate when none is synced) and checks eligibility first through `POST /api/app/bulk/preflight`, showing eligible, skipped and failed counts with the server's reasons; confirming posts one run with one request key per dialog and opens `BulkResultSummary`, which follows the persisted run. The client panel has no bulk sends. `services/leads/bulk-options.ts` reads the approved templates (raw status `APPROVED`) and the capability answer.
  - **Navigation.** "Leads" is the client panel's second item and takes a bottom-tab slot on phones; "Pricing" stays in the sidebar and moves to "More" below 1024 px (at most four bottom tabs). The operator console reaches its scoring tab from the lead console's tabs.
  - **E2E seam.** `POST /api/test/leads` (test-control only: DEMO + flag + token, 404 otherwise) ingests MANUAL leads through the real `ingestBatch`, because no source simulator produces a Devanagari name or an exact count of 51 leads.
  - **Files outside the Owns list:** `src/lib/schemas/leads.ts` (one schema set and DTOs), `src/server/services/leads/{list,stage,profile,csv,bulk-options}.ts`, `src/server/services/scoring/manage.ts`, `src/server/jobs/handlers/lead-export.ts` and its registry lines, `src/app/api/app/{leads/[leadId]/stage,leads/exports/**,scoring/**}` and `src/app/api/app/leads/_lib/workspace-query.ts`, `src/app/api/test/leads/route.ts`, the one-line `accept.ts` and the `lead-erase.ts` edits, the employee lead detail page, plus the appended shared files (schema and migration, `scoped.ts` tenant list, route manifest, `MATRIX_FIXTURES['leads.unknownExportId']`, panel nav).

### ADR-91 The documentation honesty test
- **Decision:** `tests/unit/docs/content.test.ts` fails when a docs page, `README.md` or `docs/{architecture,deployment,runbooks}.md` names something the repository does not have: an `npm run` script missing from `package.json`, an env key missing from `.env.example`, a repo path that does not exist, an app path that is not in the route manifest, an UPPER_CASE code or dotted name (job type, audit action, capability, file name) that does not occur in `src/`, `worker/`, `scripts/` or `prisma/`, or (in-app pages) a quoted message that does not occur verbatim in the code. Links must resolve (pages and anchors) and pass `safeHref`. Facts are compared with the constants they describe: the eligibility reason table with `REASON_ORDER` / `REASON_LABELS` / `DEFERRABLE_REASONS`, the Stop/Start keyword lists, the rate-limit table, and the numbers on the security, troubleshooting and data pages (argon2 parameters, password length, lockout, session limits, re-auth window, invite and reset lifetimes, worker staleness, webhook retention). It also rejects placeholder words.
- **Why:** Docs drift silently; this turns the most common drift (renamed scripts, env keys, codes, numbers) into a failing test, so the docs can only describe what is built.
- **Covered by:** the test itself, including a self-check that its checker rejects invented names.
- **Reversibility:** 5.

Statements that parallel work may change (lead sources available, capabilities checked by screens) are worded as "in this release" and carry the page's `checked` date.
- **Why:** The task forbids describing anything not built; the honesty test (ADR-91) enforces it for names, this ADR records the deliberate omissions.
- **Reversibility:** 5.

### ADR-115 Changes from the adversarial review of the LIVE-auth slice (ADR-67..69)
- **Decision:**
  - **The root layout is `force-dynamic`.** The review reproduced that an unknown URL was served from Next's prerendered `/_not-found` HTML, which cannot carry the per-request nonce: all of its scripts were blocked by the strict CSP (no security exposure, but no hydration and a console full of violations), contradicting ADR-69's "every page is dynamic". The layout now opts everything out of prerendering. `tests/unit/security/root-layout-dynamic.test.ts` pins it and `tests/e2e/security/csp.spec.ts` checks the built app (nonce on every script of `/`, `/login`, `/docs` and an unknown URL, no violations, a fresh nonce per request).
  - **Token claims use the time of the claim, and re-check the user, inside the transaction** (`redeemPasswordReset`, `redeemInvite`). Supersession and retirement are time based (the old row's `expiresAt` is set to the newer issue time); a redemption that captured `now` before its argon2 hash could still claim a token superseded during the hash, and a user disabled during the hash still got a new password. The claim now compares against `clock.now()` read inside the transaction, and the reset re-reads `status` and `isDemo` there. Tests drive a gated hasher through both races.
  - **Boot refuses LIVE with an HTTPS origin and `TRUSTED_PROXY_HOPS=0`.** `next start` does not terminate TLS, so an HTTPS origin means a reverse proxy; at 0 hops the client address is unknown for every request and the per-IP limits (login 5/min, invite/reset 10/h) collapse into one bucket shared by everybody, so a few bad requests per minute would lock every user out. Localhost LIVE runs are unaffected. Documented in `.env.example`.
  - **Test and harness hardening:** `terminate`/`killPidTree` kill the process group of children started with `detached: POSIX_DETACH`, a runner `exit` hook kills groups still tracked, `isPidAlive` treats Linux zombies as dead; `verify` locates npm for both Windows and POSIX layouts (`scripts/npm-cli.mjs`), compares real paths for its entry-point guard, forces a build for the e2e and fresh steps whatever `E2E_SKIP_BUILD` the caller exported, and fails when no step ran; the fresh-copy test skips directory entries from `git ls-files` (nested repositories and agent worktrees), crawls the manifest's `crawlAs` pages per persona plus `/docs`, and the bundle scan covers the real `re_<id>_<secret>` Resend key shape.
- **Not changed:** the public quote page gets no HSTS from the app (it sets its own hash CSP and is excluded from the proxy by ADR-57/69; the reverse proxy is where a first visit over plain HTTP is redirected). Recorded rather than fixed.
- **Why:** each item was found by an independent reviewer and either confirmed by two skeptics or reproduced during adjudication; the unfixed one is a documented exclusion.
- **Covered by:** `tests/integration/auth/password-reset.test.ts`, `tests/integration/security/boot-production.test.ts`, `tests/unit/security/root-layout-dynamic.test.ts`, `tests/e2e/security/csp.spec.ts`, `tests/unit/ops/npm-cli.test.ts`.
- **Reversibility:** 5.

### ADR-95 Integration credentials: one encrypted write path, masked reads, DEMO placeholders, and the status it leaves (T32)
- **Decision:**
  - **One write path for settings and secrets.** `POST /api/app/integrations/[kind]/credentials` (`services/integrations/credentials.ts`) takes the catalog's non-secret config fields and credential fields together, because LIVE cannot route or send without the non-secret ids (phone number ID, WABA ID, Page ID, model ID). An empty credential field keeps the saved value; re-entering a value replaces it (the rotation path). After the merge every required field of the kind must be present (422 `CREDENTIALS_INCOMPLETE`); field rules live in `src/lib/schemas/integrations.ts` and run in the browser and again in the service (`CREDENTIALS_INVALID`, field names only in `details`).
  - **Envelope and masking.** AES-256-GCM under the active kid, AAD `workspaceId|integrationId|field` (ADR-25). `secretLast4[field] = { last4, updatedAt }`, with `last4` stored only for values of at least 16 characters made of letters and digits (four characters of a short SMTP password would say too much); the read model now shows `updatedAt` for every saved value. There is no GET, reveal or decrypt route anywhere: no module under `src/app` may name a decrypt function (pinned by `credentials.test.ts`).
  - **Status after a write.** LIVE: CONFIGURED_UNVERIFIED, `verifiedAt` and the last error cleared (verification was of the old values), so sends stop until Test connection passes again (eligibility needs CONNECTED); AI drafting keeps working (ADR-55 accepts CONFIGURED_UNVERIFIED). DEMO: the integration stays SIMULATED and only `demo_` placeholders are accepted (`DEMO_CREDENTIAL_RE`), so a real secret never lands in a database whose personas have no passwords.
  - **Routing key.** A LIVE write claims `Integration.routingKey` (WhatsApp phone number ID, Meta Page ID); one already claimed by another workspace is 409 `ROUTING_KEY_TAKEN`. Revoke (`.../credentials/revoke`, typed `REVOKE`) removes every secret and sets REVOKED but keeps the routing key, so a customer's Stop on that number is still recorded; the provider is not contacted and the page says to revoke the token there too.
  - **Rate limit.** Plan §9 has no credential row and `RATE_LIMIT_POLICIES` is pinned to the plan's table, so writes and revocations use the secret-handling `inviteReset` policy (10 per hour), keyed by the person and the workspace slug.
  - **Rotation.** `npm run creds:rotate` (`scripts/creds-rotate.ts`) re-encrypts every Integration secret and every `WebhookEvent.processingPayload` under the active kid, one immediate transaction per row (no lost update against a concurrent writer), reports the envelopes still under another kid (0 when complete) and the ones no key opens (left unchanged), audits `ops.creds_rotate` with counts, and exits 1 unless both are 0. A second run changes nothing.
- **Why:** The plan fixes the cipher, AAD, masking and rotation but not where the non-secret ids are entered, what a write does to a verified integration, how DEMO keeps real secrets out, or which rate limit applies.
- **Covered by:** `tests/integration/integrations/credentials.test.ts`, `tests/components/integrations/credential-form.test.tsx`, the tenant matrix (new manifest entries).
- **Reversibility:** 4.

### ADR-96 The adapter registry resolves transports per workspace; LIVE problems become the NOT_CONFIGURED skip (T32)
- **Decision:**
  - `src/server/adapters/registry.ts` is the mode switch for provider adapters. It is pure apart from building clients: callers load the Integration and decrypt it outside any transaction (`loadIntegrationForUse`) and hand in an `IntegrationUse` (status, config, credential state ok / missing / unreadable). `resolveWhatsAppTransport` gives the demo transport in DEMO and the Cloud API transport in LIVE only for a CONNECTED or DEGRADED integration with a readable token, a phone number ID and `META_GRAPH_VERSION`; otherwise a typed problem `INTEGRATION_NOT_CONFIGURED`, `CREDENTIAL_UNREADABLE` (named first, whatever the status) or `MODE_MISMATCH`. `processMode()` reads the mode through `getConfig()`; the registry does not read `APP_MODE` itself.
  - **LIVE never reaches a demo transport.** Every LIVE branch is a `live*` function that references no demo-module symbol, and the live adapter modules never import a demo module; `tests/unit/arch/registry-live.test.ts` checks both statically and runs every status x credential state x Graph version at runtime.
  - **Dispatch.** `jobs/handlers/dispatch-run.ts` asks `services/integrations/transports.ts` for the job's workspace transport (test doubles still replace it). No transport keeps the existing path: preflight sets `integrationReady = false`, so the attempt is SKIPPED `NOT_CONFIGURED`. For `CREDENTIAL_UNREADABLE` the handler also records it on the integration in the preflight transaction (status ERROR, `lastErrorCode = CREDENTIAL_UNREADABLE`, `lastErrorRedacted = "Credential unreadable, re-enter"`, one `integration.credentials.unreadable` audit while it stands), the attempt's `errorRedacted` carries `CREDENTIAL_UNREADABLE` beside `NOT_CONFIGURED`, the inbox note reads "Not sent: Credential unreadable, re-enter.", and the setup page shows it above the credential form. Re-entering the credential clears it.
  - **Email keeps the same shape.** `resolveEmailTransport` gives the demo transport in DEMO; in LIVE `liveEmailTransport` answers `INTEGRATION_NOT_CONFIGURED` (no live email transport exists yet). T33 adds Resend and SMTP there and nothing else changes.
  - `SendPlan.template` now carries the template's raw `components` and `variableMap`, so the transport knows the header format and the quick-reply mapping (additive change to T19's preflight select).
  - The T28 constants `LIVE_CONNECTION_TESTERS` / `LIVE_TEMPLATE_SYNC` became `liveAdapters(deps)` built from the request runtime's config (`liveAdapterDepsFrom(runtime.config)`) or the boot config in jobs, so routes and tests inject the key ring, Graph version and transports.
- **Why:** The plan names the registry as the only mode switch and requires `IntegrationNotConfigured` instead of a demo fallback, but dispatch took its transports from options only and had no way to say why a LIVE send could not go out.
- **Covered by:** `tests/integration/dispatch/live-transport.test.ts`, `tests/integration/integrations/credentials.test.ts` (LIVE decrypt failure), `tests/unit/arch/registry-live.test.ts`, the existing dispatch suites (unchanged).
- **Reversibility:** 4.

### ADR-97 WhatsApp Cloud API adapter mechanics (T32)
- **Decision:**
  - Requests go through `adapters/http/outbound.ts` (the DEMO tripwire stays in front of every socket) with `Authorization: Bearer`; ids are validated as digits before they reach a URL; the access token is scrubbed from every provider text before `boundedError`. `http` and `baseUrl` are test seams only.
  - Sends: template (`language.code`, positional body parameters, a DOCUMENT header parameter by media id, one `quick_reply` button component per mapped button with its stable payload id set on this send), free-form text (`preview_url: false`), free-form document (media id, filename, caption); `biz_opaque_callback_data = attemptId` on all of them. The PDF is uploaded first as multipart media; an upload failure is PRE_SEND, RETRYABLE or PERMANENT, never AMBIGUOUS, because the message was not sent.
  - Decided locally and PERMANENT before any request: a template that cannot be sent from this app (named parameters, header variables, image/video/location headers, URL-button variables), a variable count that differs from the template body, a PDF on a template without a DOCUMENT header (`TEMPLATE_CANNOT_CARRY_DOCUMENT`; the PDF is never dropped silently and never turned into a second message), a DOCUMENT header without a PDF, an invalid recipient, empty or over-long text.
  - Outcome classes come only from the dated error map. `outboundFailurePhase` (new, shared in outbound.ts for T33) calls DNS, refused or unreachable connections, connect timeouts and TLS handshake failures "before the write" (PRE_SEND); headers or body timeouts, resets, aborts and anything unknown "after the write" (AMBIGUOUS). `Retry-After` in seconds or as an HTTP date is honoured, capped at one hour. A 2xx without `messages[0].id` is AMBIGUOUS.
  - `META_GRAPH_VERSION` is required; there is no default version.
- **Why:** The plan fixes the outbox classes and P2 but not how a template carries the PDF, which checks run before the network, or how a thrown request error is classified.
- **Covered by:** `tests/integration/contract/whatsapp-cloud.test.ts` with the documented-shape fixtures in `tests/fixtures/whatsapp/documented-shape/` (not recorded live traffic).
- **Reversibility:** 4.

### ADR-98 Template sync stores raw values and leaves unlisted templates alone; the mapping is `{ body, buttons }` (T32; amends ADR-81)
- **Decision:**
  - The live sync pages with the `after` cursor only (the `next` URL in an answer is never followed), 100 per page, at most 20 pages, and upserts by (integration, name, language) with the provider's raw status, category and components. A category change is appended to `categoryHistory`; the mapping is pruned to the positions and buttons the template still has. A template the provider no longer lists is left unchanged and counted as `missing` (no invented status: the provider refuses a send to it with 132001). ### ADR-99 Quality and limits raw, RED pauses automation through eligibility, and scheduled checks arm themselves (T32)
- **Decision:**
  - `wa.qualityCheck` reads `quality_rating` and `whatsapp_business_manager_messaging_limit` (the snippet of Meta's page names it as the replacement of the deprecated `messaging_limit_tier`; UNVERIFIED) and stores them exactly as returned, objects as compact JSON, a missing field as null ("Unknown, last checked <time>"). No tier list, tier enum or tier literal exists anywhere (pinned by `quality-limits.test.ts`).
  - Quality RED pauses automation through the existing eligibility check 6 (`QUALITY_PAUSED`, automated WhatsApp only; sends a person approves still go out, A15). It does not set `Workspace.automationPaused`, which would also hold email automation and defer instead of skip. Entering and leaving RED are audited (`integration.quality.automation_paused` with the reason, `..._resumed`), and the Integration card and setup page say "Automated WhatsApp sends are paused while the quality rating is RED".
  - **Scheduling without a scheduler.** The worker has no periodic scheduler (ADR-56), so `integration.health` (hourly re-test), `wa.qualityCheck` (hourly) and `wa.templateSync` (6 hours) arm themselves with time-bucket keys `<type>:<integrationId>:<UTC hour of the bucket>`: a manual test that ends CONNECTED or DEGRADED runs the quality check and template sync now and arms the next bucket of all three; every run arms the next bucket of every check while the integration stays CONNECTED or DEGRADED; provider failures are stored, not thrown, so a transient error never breaks the chain; an integration that leaves those statuses ends it. A scheduled re-test is audited only when it changes the status.
  - **Tester outcomes.** WhatsApp: GET the phone number and the WABA; both ids must come back as configured. Anthropic: `GET /v1/models?limit=1` then the configured (or default) model; OpenAI: `GET /v1/models` must list the configured model. A rejected key is ERROR `PROVIDER_AUTH`, a missing permission ERROR `PERMISSION_MISSING`, an unknown id or model ERROR `CONFIG_INVALID` / `AI_MODEL_NOT_FOUND`; throttling, 5xx and no answer say nothing about the credentials, so a CONNECTED integration becomes DEGRADED and anything else stays CONFIGURED_UNVERIFIED. Nothing is CONNECTED without a real answer.
- **Why:** R26 and plan §13 require raw values or Unknown and an automation pause on RED, plan §4.3 requires time-bucket keys for scheduled checks, and the T28 seam required testers that never report success without the provider.
- **Covered by:** `tests/integration/contract/quality-limits.test.ts`, `tests/integration/integrations/live-testers.test.ts`, `tests/integration/contract/templates-sync.test.ts` (scheduled sync).

### ADR-109 Extension receiver: persist-then-process, intake validation per record, lowercase token codes, CORS per token (T36)
- **Decision:**
  - `POST /api/webhooks/gmaps-extension` follows the webhook rule "verify, persist, enqueue" (plan §4.3): it authenticates, validates and stores the batch as a WebhookEvent (scope = the token's workspace, key = batchId, hash = sha256 of the raw bytes, ADR-36) and answers **202** with an intake view per record (`QUEUED` or `REJECTED INVALID_RECORD` with the field names). `ingest.process` runs `ingestBatch` as `GMAPS_EXTENSION`. The same bytes again are a replay (**200**) answered with the stored per-record ingestion results once processed (`ACCEPTED`, `DUPLICATE`, `REVIEW`, `REJECTED` + reason); other bytes are 409 `BATCH_CONTENT_MISMATCH`.
  - Each record is validated on its own so one malformed record never fails the batch; the envelope is validated whole (400), more than 200 records is 413 `TOO_MANY_RECORDS` (checked before the schema), a batch with no valid record is 422 `NO_VALID_RECORDS` and nothing is stored. Batch ids are `[A-Za-z0-9._:-]{1,128}`.
  - The stored processing body carries a server-written `intake` block (`extensionTokenId`, intake rejections). `ingest.process` (T11 file, small additive change) passes the token id to `ingestBatch` (ImportBatch.extensionTokenId) and appends the intake rejections to the stored result, so the result and its counts cover the whole delivery (ImportBatch.counts keep the valid records only). Simulated batches and events stored before T36 have no `intake` and are processed as before.
  - Token failures use the plan's lowercase codes (`token_revoked`, and in the same family `token_missing`, `token_invalid`, `token_expired`, `token_scope_missing`, `extension_not_allowed`, `web_origin_forbidden`, `origin_forbidden`); other codes stay UPPER_SNAKE. A DEMO workspace's token in a LIVE process is `token_invalid`.
  - Origin: none (non-browser client) or `chrome-extension://<32 a-p>` only; http(s) is 403, `null` and other schemes 403. The allowed extension id is per token (the plan §5.6 column), editable in the hub: a token with an id refuses any other extension Origin (403) and only its id gets `Access-Control-Allow-Origin`; the preflight is answered for an id named by any live token of this process's mode. No credentials are ever allowed in CORS.
  - Refusals are counted in WebhookRejection; refusals that belong to a known token are audited `extension.token.denied` (prefix and reason only), at most one per token per minute. `lastUsedAt` is written at most once a minute.
- **Why:** The plan fixes the contract (T8, C14, C18) but not whether the endpoint processes synchronously, how a malformed record is reported, or where the allowed extension id lives (the assignment's "per workspace" is met because each token belongs to one workspace).
- **Covered by:** `tests/integration/webhooks/extension-ingest.test.ts`, `tests/integration/extension/token-routes.test.ts`, the tenant matrix.
- **Reversibility:** 4.

### ADR-110 `extension-bridge/` is plain browser JavaScript, linted with its own globals and loaded by tests in `node:vm` (T36)
- **Decision:** `saas-sync.js` is a classic script, not an ES module, because the plan's hook is one `importScripts` line in the vendor's service worker (MV3 service workers cannot `import()` dynamically and `importScripts` cannot load modules); it is also valid as a module for a vendor worker declared `type: module`. It defines only `globalThis.AuraLeadSync` and starts itself only inside a `ServiceWorkerGlobalScope`, so `options.html` loads it for its helpers; `options.js` is an ES module. ESLint lints `extension-bridge/**/*.js` deliberately (a block in `eslint.config.mjs` with the browser, service-worker and `chrome` globals listed inline, `no-undef` on, `sourceType` script or module per file) instead of ignoring the folder; no `globals` dependency was added. `allowJs` stays false; the tests use the typed wrapper `tests/support/extension-bridge.ts`, which evaluates the script in a fresh `node:vm` context per simulated service-worker start against the fake `chrome.*` of `tests/support/fake-chrome.ts` (storage and alarms survive a restart, listeners do not).
- **Bridge mechanics:** copy-agnostic configuration (storage key, rows path, field-name candidates, settle seconds); diff by `row_key` against its own ledger (no contact data in the ledger); record id = `cid`, else `row_key`; rows wait until unchanged for the settle window (default 60 s) so late emails make the first send; a row is sent once (a later change is marked `changedAfterSend`, because ingestion never updates an existing lead, ADR-51); batches per keyword of at most 200 records and about 900 KB with a UUID batch id, stored with their exact bytes before the request; 2xx sent, 401 pauses all sending until the configuration changes ("Token revoked: ..."), 403 pauses likewise, 429 honours Retry-After, 5xx and network errors back off 1, 2, 4, 8, 16, 30, 30 minutes through `chrome.alarms`, any other 4xx moves the batch to a failed list (ids and codes only) and the next one goes; licence gate `_auth.hasValidKey === true` checked on every pass (no scan, no send otherwise); the vendor key is read only.
- **Why:** The plan asks for a plain-JS bridge with contract tests and a fake `chrome.*`, an ESLint-clean repo and an unchanged `tsc` setup.
- **Covered by:** `tests/integration/contract/extension-bridge.test.ts`, `tests/integration/chaos/extension-bridge-chaos.test.ts`.
- **Reversibility:** 4.
