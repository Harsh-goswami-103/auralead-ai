## deviations

## notes
**Calling ingestion (T11, T34-T36)**
- Call `ingestBatch(ctx, input, { contactKeyPepper: config.secrets.suppressionPepper })` with a workspace-scoped ctx (webhook, job or user).
- Input shape: `{ source, externalBatchId, simulated?, extensionTokenId?, mapping?: { version?, formId?, consent?: { column, truthyValues[], channel, purpose, noticeText, noticeTextHash?, noticeVersion? } }, records: [{ externalId, providerId?, fields: { name, phone, email, website, address, city, category, rating, reviewCount }, answers?, attribution?, submittedAt?, extractedAt? }] }`. At most 500 records.
- The result is `{ batchId, status COMPLETED|PARTIAL|FAILED, counts {received, accepted, duplicate, review, rejected}, replayed, records[] }`. Each record result has `{ externalId, status, reasonCode, sourceRecordId, leadId, mergeReviewId, consent: {outcome CREATED, consentRecordId} | {outcome NONE, reason}, replayed }`.
- Batch idempotency is on (workspace, source, externalBatchId). The content hash is a canonical sha256 of the parsed input.
  - A finished batch replays its stored results with no writes.
  - The same id with different content throws `IdempotencyConflictError`, code BATCH_CONTENT_MISMATCH (409).
  - An unfinished batch resumes.
  - ZodError means a 400; a notice hash mismatch is ValidationError CONSENT_NOTICE_HASH_MISMATCH.
- `providerId` (for example a Maps place id) becomes the PROVIDER contact key `<SOURCE>:<providerId>`.

**What ingestion writes and audits**
- Audit actions: `lead.ingest` (target Lead), `import.batch.ingest` (ImportBatch), `lead.merge_review.open` (MergeReview), `consent.capture` (ConsentRecord).
- Raw payloads are stored only after `redact()`.
- Each accepted lead gets one PipelineExecution and one `pipeline.advance` job, payload v1 `{executionId, stage}`, key `pipeline.advance:<executionId>:<stage>`. Use `enqueuePipelineAdvance` from `services/pipeline/executor.ts`.
- Ingestion enqueues nothing else.

**Pipeline executor (T12/T14/T23)**
- Register a stage by appending one import and one `STAGE_HANDLERS` entry in `src/server/services/pipeline/stages/index.ts`, for example `import { scoreStage } from './score';` then `scoreStage,`.
- Handler shape: `StageHandler { stage, run({ ctx (job AppCtx scoped to the workspace), job, stage, execution {id, workspaceId, leadId, pipelineConfigVersionId}, lead, config {id, version, approvalMode} }) }`. It returns `{status:'DONE'|'SKIPPED'|'FAILED', reasonCode?, outputRef?, finalTx?}`.
- Do every write in `finalTx(tx)`. The tx is the raw client, so write `workspaceId` explicitly. `finalTx` commits atomically with the StageRun, `currentStage`, the next job and the audit row (`pipeline.stage.done|skipped|failed|waiting`).
- Do network calls in `run`, never in `finalTx`.
- Throwing a retryable AppError retries the job. Any other throw marks the stage FAILED (STAGE_ERROR) and the job DEAD.
- A stage halted with STAGE_HANDLER_MISSING already has a SUCCEEDED job under its key. To resume it once the handler exists (T23), enqueue a new `pipeline.advance` job under a different idempotency key; the executor treats a PENDING run as runnable.
- `stageOrder(graph)` returns the topological order or null. The full graph validator (P11) is still T23's.
- Tests can call `createPipelineAdvanceJob({ stages, mode })` with stub stages and run it through `createWorker(...).tick()`; see `tests/integration/pipeline/executor-idempotency.test.ts`.

- `src/server/services/messaging/consent.ts` exports `captureIngestionConsent`, `findCapturedConsent`, `isTruthyAnswer`, `noticeTextHash` and `consentSourceFor`. T18 owns the rest of that file (manual grants, re-opt-in and suppression clear).
